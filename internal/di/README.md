# di

概要:  
このディレクトリは、アプリケーション全体の **依存性注入（Dependency Injection / DI）を統括的に管理するレイヤー** です。  
Uber FX を利用し、各レイヤー（config / logging / observability / database / infrastructure / usecase / controller / server）の  
**依存関係の組み立て・ライフサイクル管理・モジュール化** を行います。

アプリケーションの起動シーケンスやレイヤー間依存を明確化し、  
「何がどこで初期化され、どの順序で適用されるか」を 1 箇所で一元管理する中心的な役割を持ちます。

## 役割

- Uber FX による DI コンテナの初期化
- 各レイヤー（core / module / server）の fx.Module を統合
- アプリケーション起動 (`Start`) / 終了 (`Stop`) のライフサイクル制御
- 本番・開発に共通するアプリケーションブートストラップ
- サーバー起動に必要な構成をまとめた **NewApplicationServer** の提供

`internal/di` は **アプリケーション全体の依存関係を構成する「中心ノード」** です。

## 必要度

### 本番運用での必須度

- 必須度: **本番運用で必須**

理由:  

- 本番環境では、設定（Config）、ログ（Zap）、トレース（Otel）、DB接続など  
  クリティカルな依存関係を安全に初期化し、順序よく起動させる必要があるため  
- shutdown シーケンスを fx が管理することで、安全にリソース開放できる  
- サーバー拡張（middleware / instrumentation / security）が正しく適用されるため  

### 開発/テスト運用での必須度

- 必須度: **開発/テスト運用で必須**

理由:  

- ローカル開発でも依存構造を本番と同一に保てる  
- E2E / 統合テストでサーバー起動を簡素化できる  
- 依存関係を手で配線しないため、開発者の認知負荷低減に大きく寄与  

## 無効化した場合の影響

- DI が機能しないため、アプリケーションが起動しない
- ミドルウェアやサーバー層が依存解決できず HTTP API が動かない
- Config / Logger / DB など重要リソースの初期化順序が保証されない
- ライフサイクル管理が失われ、shutdown が安全に完了しない

**無効化するとアプリケーション全体が動作不能になるため、必須のコンポーネントです。**

## 注意点

- 新しい機能を追加する際は **必ず fx.Module として切り出し、ここから読み込む**  
- domain や usecase から DI パッケージを参照してはいけない（依存逆転が壊れる）  
- DI は「外側の層」なので、アプリケーション内部への逆参照は禁止  
- `NewApplicationServer()` にモジュールを追加する際は **適切な順序** に注意  
- fx.In / fx.Out による構造化依存注入を理解した上で変更すること
