# outbound

概要: `outbound` は **HTTP レスポンス（出力）側の処理を拡張するためのミドルウェア DI モジュール群** をまとめたディレクトリです。  
リクエスト処理後の **レスポンス変換 / エラーハンドリング / 出力形式の強制 / パニック回復（リカバリ）** を担当します。

本番運用で必要不可欠な「HTTP の出口側の安全性と統一性」を担保するレイヤーです。

## 役割

- **Recovery（パニックハンドリング）**  
  - panic をキャッチし、500 エラーとしてログ出力 & 統一レスポンスを返す  
  - サーバークラッシュを防ぎ、安定稼働を保証

- **ErrorHandler（エラーハンドリング統一化）**  
  - アプリケーションエラーを HTTP レスポンスへマッピング  
  - ログ・トレース・レスポンス形式を統一化

- **ForceJSON（レスポンス強制 JSON 化）**  
  - 返却形式が明確でないルートでも JSON 形式に統一  
  - OpenAPI やフロントエンドとの整合性を保証

これらのミドルウェアは **Echo のレスポンス処理（Outbound 処理）を強化するための必須コンポーネント**です。

## 必要度

### 本番運用での必須度

- 必須度: **本番運用で必須**

理由:  

- Recovery がないと panic によりサーバーが落ちる可能性がある  
- ErrorHandler がないとエラー形式が統一されず、監視や分析が困難  
- ForceJSON がないとレスポンス仕様が揺れ、クライアントが誤動作する可能性がある

特に **ErrorHandler + Recovery の 2 つは、商用運用における最重要ミドルウェア**です。

### 開発/テスト運用での必須度

- 必須度: **開発/テスト運用で推奨**

理由:  

- panic 発生時に原因が追いやすくなる  
- テスト中でも API のレスポンス形式が揺れないため、テストケースが安定  
- エラー形式が統一されているため、E2E / integration テストで利便性が高い

開発でも積極的に導入すべき領域です。

## 無効化した場合の影響

- panic により API サーバーがクラッシュする危険がある  
- エラー JSON が統一されず、API の可観測性が著しく低下  
- クライアントが想定外のレスポンスを受け取り、障害を引き起こす可能性  
- ログ・トレースの相関性が崩れ、障害解析が困難になる

**→ 本番運用では無効化してはいけない層です。**

## 注意点

- Priority は `extension.UseMiddleware` のルールに従って設定されており、  
  他のミドルウェアと順序が衝突しないように調整されています  
- Recovery は **最初に動くべきミドルウェアのひとつ**  
- ErrorHandler は Echo の `HTTPErrorHandler` を置き換えるため ServeCfg として提供されます  
- Outbound ミドルウェアは controller 層であり、**domain/usecase に依存させない**こと  
- 追加のレスポンス処理を行う際は、このディレクトリへ新しい outbound ミドルウェアを追加するのが推奨
