# Repo Truth

このリポジトリについて*いま*何が真かを、その一次資料から、推論の道筋が見える形で答える。

## 使うとき

- どこで実装されているか、経路が実際にどう振る舞うかを問われたとき。
- ここでの規則・規約・正本の文書は何かを問われたとき。
- なぜその設計なのかを問われたとき。
- 手順・規則・用語がそもそも存在するのかを問われたとき。

以下には使わない: リポジトリ固有の答えを持たない一般的なプログラミングの問い、手順が文書化された既知の運用症状（`repo-ops`）、選択肢の比較が要る未決の設計問題（`research`）、差分のレビュー（`impl-review` / `test-review` / `comment-sweep`）、見つけたものの起票（`new-issue`）。

## 契約

| | |
| --- | --- |
| **所管** | repo 内の現状の事実回答、事実と推論の分離、未定義 / 確認できず の判定 |
| **しないこと** | repo 外の一般論を主根拠にした将来設計 / 未決の採択 / 変更 / 見つけた drift の修復 |
| **開始条件** | 現状・規約・根拠・語義・存在有無を問われたとき |
| **停止条件** | 二つの権威が矛盾したとき（提起して停止）、索引を通読しないまま断定を求められたとき |

## なぜ必要か

このリポジトリについての誤答はほぼ 2 つの失敗から出ていて、どちらも「もっとよく読む」では直らない。

**1 つ目は記憶から答えること。** 層の規則、make target の挙動、ステータスコード —— どれも思い出せる気がするし、
どれもその後変わったファイルで決まっている。自信のある語調で述べた答えは実行に移される。だいたい合っている
ことは、確認していないと言うことより悪い。

**2 つ目は誤ったコピーを読むこと。** ここでの探索空間は積極的に誤導してくる。追跡されている `*.md` およそ
1,000 件のうち 4 割超は `AGENTS.md` が読むことを禁じている `*.ja.md` 対訳であり、`docs/portal/**` /
`docs/godoc/**` / `docs/db-schema/**` / `docs/openapi/**` / `docs/coverage/**` は元に遅れて追随する生成物で
ある。これらは*追跡されている*ので `.gitignore` を尊重する検索では除外されず、原本と同じだけ上位に来る。
したがって統べるファイルを突き止めることは読むこととは別の工程であり、答えが正しいかを決めるのはその工程の
ほうである。

このスキルの出力が 根拠 と 推論 を分けているのはそのためである。要点は不確かさへの丁寧さではなく、根拠が
見えている主張だけが読者に覆せる、ということである。

## 引数と入口の確認

このスキルは開始前に何も聞かない。スコープを確認するモーダルは、たいていの答えの価値より高くつく。変わりうる
ものは代わりに引数で表し、チェーン呼び出し側がこのスキルに推測させずに述べられるようにする:

| 引数 | 効果 |
| --- | --- |
| `--depth=quick`（既定） | 所有索引を拾い読みする。**未定義 は使えない** —— 欠落は 確認できず としてしか報告できない |
| `--depth=full` | 所有索引を通読する。未定義 を報告する資格が生じるのはこれによる |
| `--kind=<kind>` | Step 1 の分類を飛ばす。呼び出し側がどのコーパスが統べるか既に知っている場合 |

`--depth` が本当のダイヤルであり、これは意図的に「権威ある不在」のコストそのものになっている。110 件の ADR
エントリと README 連鎖を通読するのは高くつくし、ポインタさえ要るだけの問いにそれを払わせるべきではない。
答えが「何かが存在しないこと」に懸かっていると判明したら自分で `full` へ上げる —— そして上げたと述べる。

**そのうえで、自分が正しい入口かを確認する。** ここには 3 つのスキルが隣り合っており、区別する信号は語彙では
なく意図にある。同じ名詞が 3 つとも出てくる:

| 問い手が述べているもの | 入口 |
| --- | --- |
| 壊れたもの、落ちたゲート | `repo-ops` |
| 実行したい操作 | `how-to` |
| まだ誰も決めていない選択 | `research` |
| どう動くか、規則は何か、存在するか | ここ |
| 上のどれとも読めてしまうもの | `question` —— 聞いてくれるルーター |

入口が違うなら 1 行でそう述べ、正しい先を名指す。そのまま答えるのは誤発火より悪い。手順が要る人に対して、
知識の答えの形をした答えが返るからである。

一番効くのは最後の行である。裸の「今」や「どうなの」は、外の世界を指すことも、今あるこのリポジトリを指すことも、
この窓の差分を指すこともあり、コードをいくら読んでもどれかは決まらない —— 曖昧さは問い手の中にある。読みを
選ばずに `question` へ送ること。選べば、誰も聞いていない問いに自信のある答えが返る。

Graphify 自身の description は、コードベースへの問いはまずグラフクエリとして扱えと主張しており、この
checkout には `graphify-out/` があるので、その主張は常に成立している。あれはインストール済み依存物に対する
上流の文言であって、このリポジトリのルーティングではない。グラフは**このスキルが使う道具**（Step 2）であり、
リポジトリへの問いはやはりここへ来る。グラフの結果には、根拠と推論の分離も、探索範囲も、未定義 / 確認できず
の区別も無いからである。

## Step 1 — 何を問われているかを分類する

分類は「何が答えになるか」を決め、さらに重要なことに「不在が何を*意味するか*」を決める。検索の前に行う。

| 種類 | 何が答えになるか | 不在が意味するもの |
| --- | --- | --- |
| 事実 — どう振る舞うか | リクエスト経路上の実装 | その経路が存在しない。それらしい経路を描写せずそう述べる |
| 規則 — ここでは何をすべきか | 統べる文書 | **規則が未定義かもしれない** —— それ自体 findings だが、Step 2 が所有索引を尽くした後に限る |
| 根拠 — なぜこうなっているか | `docs/adr/`、`docs/design/` | 決定が暗黙に行われ、記録されなかった |
| 手順 — ここではどうやるか | `.makefiles/**`、`.lefthook.yaml`、`.github/workflows/`、`docs/maintenance/` | **正規手順が存在しないかもしれない** —— 同じ基準。穴を埋めるためにコマンドを発明しない |
| 語彙 — この用語の意味は | `docs/spec/glossary.md`、`docs/spec/{domain,usecase}/` | 業務語彙でないか、登録されないまま漏れ出している |
| 履歴 — いつ・なぜ変わったか | `git log`、マージ済み PR | — |

問いはしばしば、どの種類なのかについて言われざる前提を抱えている。「統合テストだけ回すには？」は 手順 の問い、
「なぜ統合テストに DB slot が要るのか？」は 根拠 の問いであり、解決するコーパスが違う。

## Step 2 — 探索範囲を確定し、そのうえで出典を突き止める

このスキルが存在する理由の工程であり、答えが信用できるかを決める工程でもある。

**一度も開いていないファイルからは何も結論できない。そしてこのコーパスは、偶然開いていたと言えるほど小さくない。**
canonical な Markdown 518 件（`*.ja.md` 対訳 495 件と生成コピー 144 件を除いた数）、ADR 110 件、パッケージ
README 150 件、`.mk` 52 件 —— コードは別である。何を読んでも大半は未読のまま残るので、*ヒットが無いことは
答えが無いことではない*。

grep はこれを救わない。`AGENTS.md` がその理由をそのまま書いている: **文書はそれが所有する関心事で命名される**
ので、索引を機能の言葉で検索するのでは足りない。問いを統べるファイルは、その問いのどの語も名前に含まない
ことが普通にある。

### 索引優先で、関心事から探す

索引を読み、キーワード一致ではなく*何の関心事を所有しているか*でエントリを選ぶ:

| 索引 | 何を覆うか |
| --- | --- |
| `docs/adr/README.md` | なぜその決定がなされたか —— 110 件 |
| `docs/design/README.md` | サブシステムや横断的関心事がどう動くか |
| `.makefiles/README.md` | 全 make target、領域ごと |
| 対象パスから層のルートまでの README 連鎖 | 責務・禁止事項・設計意図 —— 150 件あるが、効くのは連鎖だけ |
| `docs/spec/glossary.md`、`docs/spec/{domain,usecase}/` | 業務語彙と機能ごとの挙動 |

`.claude/skills/repo-ops/SKILL.md` の §0「正本の見つけ方」が、答えの対象 → 出典の正本表であり、ノイズを
除いた検索の呼び出しと「権威に見えるが違う」ファイルの一覧も持っている。実行時に読むこと。ここへ複製しない —
維持されているのはあちらである。

キーワード検索は**最後**に来る。索引が取りこぼしたものを拾う網であって、主たる手段ではない。

### 結論の前に探索範囲を記録する

実際に覆った範囲を把握しておく —— どの索引を通読したか、どの README 連鎖を辿ったか、どの glob を検索したか、
**そして、どの掃引を回さないと決めたか（理由つき）**。覆った分だけを並べた探索範囲は、残りを除外したのか
忘れたのか読み分けられない。findings になるのは前者だけである。
これは事務作業ではない。不在を反証可能にするものであり、このスキルが曖昧にしてはならない線を引く:

| 判定 | 必要なもの |
| --- | --- |
| **未定義** —— 規則 / 手順が存在しない | 所有索引を**通読**し、README 連鎖を辿ったこと |
| **確認できず** —— 確立できなかった | それに満たないすべて |

確認できず へ落とすのはいつでも可能で、コストはゼロである。部分的な掃引から 未定義 を報告するのは、答えが
無いことより悪い。確定した事実として読まれ、次の人がその上に積むからである。

`repo-ops` §0 が定めていて、このスキルが緩めてはならないことが 2 つある:

- **`*.ja.md` を決して読まない。** ヒットすること自体は*位置特定*として有用だが —— その話題が文書化されている
  証拠になる —— 読むのは隣にある英語原本である。
- **出典が食い違ったときの優先順位**は `AGENTS.md` → `docs/rules.md` → `docs/architecture.md` → ユーザー指示。
  設計意図と実装方針については **README > Code > SKILL**。

### 構造がテキストに勝つところではグラフを使う

キーワード検索は、この節が冒頭で挙げた問いでこそ失敗する —— 関心事で命名された統べる文書、呼び出し先と語彙を
共有しない呼び出し元。Graphify は**構造**を索引しているので、テキスト検索が届かないところへ届く。使うこと。
避けて通るだけにしない。

ここで元が取れるコマンドは 2 つ（上流の主張ではなく、このリポジトリ上で実測されたものが `.claude/README.md`
にある。他へ手を伸ばす前にその節を読む）:

```bash
# 影響範囲 / 呼び出し元 —— 「これをしているのは X だけ」というあらゆる主張への答え。
# ノード id を取るのでラッパー経由で。シンボル名を解決し、候補を並べてくれる。
node .claude/scripts/graph-affected.ts <symbol> --depth 2

# 構造的な検索。既定の budget（約 2000 トークン）はこの規模のリポジトリでは切り詰められ、その旨を出力する ——
# 上げるか、切り詰め警告を読むこと。答えは切られた側にあるかもしれない。
GRAPHIFY="${XDG_CACHE_HOME:-$HOME/.cache}/go-boilerplate/graphify/bin/graphify"
"$GRAPHIFY" query "<question>" --budget 8000
```

`affected` が元を取るコマンドである。逆方向の走査は各呼び出し箇所を関係ラベルと `file:line` 付きで返し、
それはスコープ主張が必要とする網羅的探索の証拠そのものである。`god-nodes` は無視すること —— エッジ数で
順位付けするので、このリポジトリの 1:1 テスト対応規則によりテストの足場が production code より上に来る。
誰も聞いていない問いに答えている。

そのうえでガードレール。上のどれも縮めない:

- **ノード・エッジ・生成された要約は決して根拠ではない。** それはファイルに到達した経路である。そのファイルを
  開いて引用すること。ソースで裏取りしなかったグラフの答えは 推論 のままである。
- **使ったときは必ず鮮度を述べる。** `graphify-out/GRAPH_REPORT.md` の `Built from commit:` 行を
  `git rev-parse HEAD` と比べ、グラフがどのコミット時点かを述べる。未コミットの作業についての問いにはグラフは
  盲目なので、作り直す（`make graphify-update`。固定版で走る）か `grep` を使う。
  小さな差分なら後者のほうが安い。
- **無いのが普通である。** gitignore されておりマシンごとにインストールされるので、索引読み・検索・`git log`・
  直接読解へフォールバックする —— そして探索範囲にはそのように記録する。回せなかった構造的掃引は、覆えなかった
  範囲の一部だからである。

## Step 3 — 一次資料を読み、継ぎ目に印を付ける

引用するものは開く。読んでいないパスは根拠ではない。

読み進めながら 2 つの山を分けたままにしておく。1 つの段落に書いた瞬間に混ざるからである:

- **根拠** —— 出典が実際に含んでいる文、またはコードが実際に表している挙動。
- **推論** —— 出典を組み合わせて、不在から、あるいは兄弟との類推から結論したもの。推論は正当であり、答えの
  価値そのものであることも多い。正当でないのは、それを根拠と同じ語調で提示することである。

一番よくある漏れは*スコープ*の主張である。「これをしているのは X だけ」は不在についての主張であり、不在は
網羅的探索で確立されるか、まったく確立されないかのどちらかである。呼び出し箇所を推測せずグラフを逆走査する
（`node .claude/scripts/graph-affected.ts <symbol> --depth 2`）。それも網羅的探索も行っていないなら、実際に
覆った範囲まで主張を狭める。

## Step 4 — 鮮度と矛盾を確認する

- **鮮度。** 統べるファイルが今週動いているかもしれない。答えがそれが最新であることに懸かるなら、引用する
  パスの履歴を確認する（`git log --oneline -10 -- <paths>`）。
- **矛盾。** どちらも権威を主張する 2 つの出典が食い違ったら、両方を鮮度付きで報告する —— 問いに答えるほうを
  黙って採らない。`AGENTS.md` の *Conflicting Authority* 節がこれを統べており、それは意図的である。食い違いに
  気づくことが仕事で、解決することは仕事ではない。
- **drift は findings であって作業ではない。** コードとその README が食い違うなら、README が統べる側で
  コードが drift である。そう述べて止まる。修復は `back-prop` の担当であり、統べる文書をコードに合わせて
  「訂正」するのはそもそもこのスキルの裁量ではない。

## Step 5 — この契約で答える

常にこの形、日本語で。回答 は最初に読める長さに保つ。

````markdown
## 回答
<結論を 1〜3 文で>

## 根拠
- <主張> — `<path>` の `<symbol / target / 節>`
- <主張> — `<path>` の `<symbol / target / 節>`

## 推論
- <根拠から導いたこと。断定と区別できる書き方で>

## 矛盾 / 欠落
- <食い違う出典と、それぞれの鮮度> / <未定義 または 確認できず> / <古い可能性のある記述>
- 探索範囲: <通読した索引 / 辿った README 連鎖 / 検索した glob / 回さなかった掃引とその理由>
  ← 欠落を報告するときは必須

## 確度
High | Medium | Low — <そう判断した理由>

## 次にできること
<追加確認 / research / new-issue / ADR 化 / back-prop など。実行はしない>
````

引用は**シンボルとパスで行い、行番号では決して行わない** —— 行番号は次のリファクタで古くなり、それを辿って
誤った場所に着いた読者は、そこにあるものを信じてしまう。

確度は、どれだけ確信があるかではなく出典で判定する:

| 段階 | どんなとき |
| --- | --- |
| High | 最新の一次資料が複数一致し、かつ問われた問いを統べている |
| Medium | 一次資料が単独、暗黙、または鮮度が未検証 |
| Low | ほぼ推論、出典が矛盾、または決め手となる出典に到達できなかった |

問いの一部しか答えられなかったときは、検証できた部分を返し、残りを欠落として名指す。正確な部分回答は、
完結して見える回答に勝る。

## 欠落は答えである

「これに正規手順は存在しない」はこのスキルが所管する findings であり、存在する理由は代替がもっと悪いから
である。発明されたが尤もらしいコマンドは、文書化されたコマンドとまったく同じに読め、次の人がそれを実行する。

結果として述べ、探索範囲を添えて、不在を反証可能にする:

> 正規手順は**未定義**。`.makefiles/README.md`（全 target）と `docs/maintenance/` の索引を通読し、
> `.lefthook.yaml` / `.github/workflows/` を確認したが該当なし。近いのは `<target>`（ただし〜の点で
> 目的が異なる）。

索引を通読していないなら判定は **確認できず** であり、どの索引を読み残したかを述べる。この 2 つは交換可能では
ない。一方はリポジトリについての findings で、もう一方はこの実行がどこまで進んだかについての findings である。

`repo-ops` はどちらの判定も意図的に持たない —— 既知症状の lookup table であり、「未定義」と結論することを
教えれば汎用の検索スキルに変わってしまう。症状がその索引に無いとき、問いはここへ来る。

## 単独で成立する設計

このスキルはそれ自体として起動され、何にもチェーンしない。`次にできること` が何になるかを報告し ——
未決の設計問題なら `research`、見つけたものの起票なら `new-issue`、drift なら `back-prop`、既知症状なら
`repo-ops` —— 回すかどうかはユーザーが決める。

3 つのレビュースキルが `AGENTS.md` の Review Phase Protocol の下で peer である理由と同じである。次を代わりに
回すスキルはその決定をユーザーから取り上げ、そしてこのスキルの判断が drift したとき、そこを通った全フローが
黙って振り替えられることになる。

## やること / やらないこと

- ✅ 索引優先で関心事から探す。キーワード検索は最後の網に留め、最初の一手にしない。
- ✅ 探索範囲を記録する —— 通読した索引、辿った README 連鎖、検索した glob。
- ✅ 所有索引を尽くしていないときは常に 確認できず と言う。未定義 は尽くしたときに限る。
- ✅ 引用する出典はすべて開く。シンボルとパスで引用する。
- ✅ 根拠 と 推論 を別の節に保つ。
- ✅ 矛盾は両方の出典と鮮度を添えて報告する。
