# Glossary

`docs/spec/glossary.md`——このシステムの業務語彙の正本——を保守する。

## このスキルが決めること、決めないこと

機械が決められることを決める。どの識別子が存在するか、どれに行が無いか、どれが二重に定義されて
いるか、どれがもう解決しないか。**正名は決めず、2 つの語が同義であるとも宣言しない。**

この線引きは慎重さではなく、根拠が尽きる場所である。識別子の衝突は文字列の比較だが、2 つの定義が
実際に*違う*かどうかは散文の読み取りである。違う 2 語が 1 つの概念を指していることには機械的な痕跡が
一切残らない——人が両方の行を読んで気づいたときにだけ表面化する。そしてどの名前が勝つかは、業務が
これからどう話すかについての決定であり、コードがいくら在っても供給できない。

findings を報告し、文言を提案し、判断は渡す。

## 使いどころ

- feature が入り、その新出用語が用語集に無い
- ある業務語の意味を問われた、あるいは 2 つの語が同じ意味かを問われた
- 用語集がコードに対して古びて見える
- 定期的な語彙の棚卸し

使わない場面:

- feature 自身の spec — `new-spec` / `new-spec-domain`。spec の書式 — `verify-spec`
- Evans 原義との DDD パターン照合 — `ddd-audit`
- README / ADR へ漏れた業務語彙 — `back-prop` の glossary 検出器

## Step 0. スコープを確認する

`AskUserQuestion` を 1 問。

```text
質問: どこまで見ますか？
選択肢:
  - 全体（既定。全 feature と domain 全体を突き合わせる）
  - 特定 feature のみ（--feature <name>。新出用語の登録向け）
```

## Step 1. 器をベースラインとして読む（決定的な処理。委譲しない）

`docs/spec/glossary.md` を読む。この実行が依存する 3 つがそこにあり、いずれも本文にハードコードしない。

- 既存の行（用語・所有・コードシンボル・公開名）
- **Mechanism vocabulary** 節——業務語ではないと既に判断された名前
- **Watch list**——既知の同音異義と同義

Mechanism 節は抑制のチャネルである。**orphan の集合を報告する前に必ず差し引くこと。** 毎回同じ構造名を
提案し直す棚卸しは誰も読まなくなる。この節はまさにその失敗を防ぐために在る。

器が存在しない場合はそう述べて停止する。器を作ることは規則を含む設計行為であり、このスキルは器を
埋めるのであって、器を発明しない。

## Step 2. インベントリを抽出する

3 つの一次情報。いずれも実行時に読む。

```sh
# spec が宣言している用語
grep -n '^package:\|^struct:' docs/spec/*/domain.md

# domain の公開型
grep -rn '^type [A-Z][A-Za-z0-9]* \(struct\|interface\)' internal/domain --include='*.go'

# 公開名
ls openapi/components/schemas/
```

`_test.go` と `mock/` は除く。YAML の形は仮定せず `.claude/scaffold-spec/domain-spec.md` を実行時に
読む——節の一覧はあちらが変えるものである。

用語の所有は、spec が置かれている feature ディレクトリと、そこが宣言する集約である。1 つの用語に
所有が 2 つあるのは、突き合わせて直すデータ上の問題ではない。それが findings である。

## Step 3. 4 種の findings を分けて扱う

求められることが違うので、1 つの一覧に混ぜない。

- **新出用語** — spec が宣言しているが用語集に行が無い。spec 自身の散文から定義文の草案を起こして行を
  提案し、人が書き換えられるようにする。**生成されたように読めてはいけないのは、この定義文である**
- **orphan** — `internal/domain/**` で公開されているが、どの spec にも用語集にも無く、機構語としても
  記録されていない。**誰も書き留めなかったものを捕まえられるのはこの findings だけである。**他はすべて
  文書から出発するので、一度も文書化されなかった語は見えない。orphan の決着は 3 通り——行になる、
  Mechanism vocabulary へ回る、コード側の命名が誤りである
- **解決しない参照** — spec の `package` か `struct` がもう存在しない。決定的であり常に欠陥だが、
  どちら側が誤りかはこのスキルの判断ではない
- **同音異義** — 1 つの識別子を 2 つの feature が宣言している。両方の定義を並べて報告し、本当に同じ
  概念かを問う。**その問いにここで答えないこと**

## Step 4. findings ごとに判断を返す

`AskUserQuestion`、1 回の呼び出しは 4 件まで。選択肢は findings が支えるものに従う——orphan なら
「用語として登録」/「機構語として記録」/「コード側の命名が誤り」/「今回は保留」。

新出用語では草案の定義文を提示し、**書き換えるほうを楽な道にする。誰も編集していない定義は、誰も
合意していない定義である。**

## Step 5. 書き込む

`docs/spec/glossary.md` だけを書く。spec ツリーは英語見出し + 日本語本文の単独ファイルで、
**`.ja.md` のペアを持たない**。ペアを作らず、`canonicalize-doc` も繋がないこと。

サンプル由来の行は `sample-api:begin` / `sample-api:end` マーカーの内側に置き、サンプルと共に去るように
する。撤去後も残る用語の行は外側へ置く。ここを誤ると、**もう存在しない用語をページが語り続ける**。

feature の spec・README・ADR・DDD 台帳・実装コードには触れない。コード側の改名が要るものは、ここで
編集するのではなく申し送りとして提示する。

## Step 6. 締め

日本語で報告する。追加した行、分類した orphan、解決しない参照、未決のまま残した同音異義。他スキルの
担当になるものは名指しして終わる。commit / push はしない。

## AI Modification Scope

- 読み込み: `docs/spec/**`、`internal/domain/**`、`openapi/**`、`.claude/scaffold-spec/domain-spec.md`
- 書き込み: `docs/spec/glossary.md` のみ
- 触らない: feature の spec、README、ADR、DDD 台帳、実装コード、生成物、`AGENTS.md`

## Constraints

- ❌ 正名をスキルが決める（どの名前が勝つかは業務の話し方の決定）
- ❌ 同義を機械が判定する（機械的痕跡が無い。提示までにとどめる）
- ❌ Mechanism vocabulary を差し引かずに orphan を報告する（毎回同じ一覧が出て読まれなくなる）
- ❌ 器が無いときに器を作る（規則を含む設計行為であり、このスキルの担当ではない）
- ❌ `docs/spec/glossary.md` 以外への書き込み、`.ja.md` ペアの作成、commit / push
- ✅ 4 種の findings を分けて報告（求められることが違うため）
- ✅ サンプル由来の行は `sample-api` マーカーの内側へ
- ✅ 出力は日本語
