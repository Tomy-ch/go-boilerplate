# Research

開いた問いを、人間が実際に決められる決定へ変える。あるいは、そもそも開いていなかったという findings へ変える。

## 使うとき

- 設計・技術・運用の選択が開いていて、まだ誰も選んでいないとき。
- 選択肢を求められたとき、あるいは普通はどうするのかと問われたとき。
- 決定が見直されており、トレードオフをもう一度並べる必要があるとき。

以下には使わない: リポジトリの現状の確認（先に `repo-truth`）、既に決まった issue の実行（`impl-issue`）、
結果の起票（`new-issue`）、差分のレビュー（`impl-review` / `test-review` / `comment-sweep`）。

## 契約

| | |
| --- | --- |
| **所管** | 未決の比較、評価軸の確定、推奨とその反転条件、決めるべきことの提示 |
| **しないこと** | 採択 / ADR 承認 / 実装 / 案数合わせの選択肢捏造 / 出典・数値の捏造 |
| **開始条件** | 選択が開いていて、まだ誰も決めていないとき |
| **停止条件** | 現状が不明（`repo-truth` へ）、既に ADR / spec が決めている、外部情報を確認できない |

## なぜ必要か

比較を比較しないことより悪くする失敗が 3 つあり、どれも入念さのように見える。

**軸が答えから逆算される。** 好ましい案がいったん存在すると、それを有利にする基準のほうが書き留められる。
軸を先に固定することだけが防御であり、それはどの案も名指す前に行われなければならない。

**コストが答えを選ぶ。**「それだと 30 ファイル触ることになる」が、いつのまにか決め手の論拠になる。
`AGENTS.md` の *What to Recommend* 節は、このリポジトリでは品質と一貫性がそこへ至るコストに優ること、そして
コストは人間が方向を保ったまま範囲を断れるように述べられるのだ、と明言している。コストを述べることは必須で
あり、コストに選ばせることは必須ではない。

**証拠が捏造される。** ベンチマークの数値、バージョン、「一般に推奨されている」—— どれも作るのは簡単で、
作られたものだと気づくのは難しい。比較の自信ある語調に置かれた未検証の主張は、誰も辿り直せない決定の
根拠になる。

このスキルが防ぐためにあるものがもう 1 つあり、そちらはより気づきにくい。**そもそも開いていなかった問いに
答えてしまうこと。** Step 1 を見よ。

## 引数

| 引数 | 効果 |
| --- | --- |
| `--stage=full`（既定） | 推奨まで通す |
| `--stage=dissolve` | Step 0-1 だけ回して止まる —— 既に決まっていないか、同型の前例が無いか |
| `--sources=repo` | repo の証拠のみ。未検証の外部主張を出すくらいなら出さない |
| `--sources=external`（既定） | 外部参照を許可。出典は Sources 節に従って明記する |
| `--axes=<csv>` | 呼び出し側が評価軸を固定する。Step 2 は選ばずにそれを採用する |

`--stage=dissolve` が安いモードであり、しばしばそれが答えのすべてになる。ここへ来る問いの多くは、既に
決着しているか、コードベースが解いた何かと構造的に同一である。「これはそもそも開いた問いなのか」が問いの
ときはこれに手を伸ばす —— そして解消したことを、比較の失敗ではなく結果として報告する。

`--sources=repo` は参照が使えないときの正直なモードである。劣化した実行ではなく、推測を拒否する実行であり、
したがって「その結果できなかった主張はどれか」を述べなければならない。

## Step 0 — その問いが本当に開いているかを確かめる

現在のコードについて誤った前提の上に建てた比較は、比較しないことより悪い。決められそうに見えるからである。

何よりも先に現状を確定する —— 何が存在し、何が制約し、`docs/adr/` や `docs/design/` に既に決定が立っている
か。その状態が不明または争点なら、**止まってそう述べる**。ユーザーは先に `repo-truth` を回すべきである。
自分で起動しないこと。そして仮定で穴を埋めないこと。その仮定が以後すべての選択肢を黙って形作ってしまう。

ADR や spec が既にこれを決めているなら、それが答えである。それを報告し、論拠が今も成り立つかを述べ、止まる。
決着した決定を再び開くのは人間の判断である —— `AGENTS.md` は、前例は認可ではないと明言している。

**その決定はキーワードではなく関心事で探す。** `docs/adr/` には 110 件の記録があり、`AGENTS.md` は、文書が
それの所有する関心事で命名されている以上、索引を機能の言葉で検索するのでは足りないとはっきり述べている。
`docs/adr/README.md` と `docs/design/README.md` のエントリを読み、それぞれが何を統べているかで選ぶ。この
やり方で見落とされた決定はエラーとしては表に出ない —— 既に決着したことを蒸し返す比較として表に出る。それが
このスキルが出しうる最も高くつく出力である。

## Step 1 — まず同型の機構を探す

これを設計問題として扱う前に、構造的に同一の問題をリポジトリが既にどこかで解いていないかを確認する。解いて
いるなら、配置・構築・呼び出し位置はその前例で既に決まっており、選択肢を採点することは存在しない分岐を
でっち上げることになる。

これは最も安く、最も頻繁に飛ばされる工程である。新しいものを所有するであろう層を探し、次にその兄弟、次に
`pkg/` を探す。問題の形から推論せず、`docs/architecture.md` と所有する `README.md` を実行時に読む。

**同型の機構はその形で見つかる。つまりキーワード検索では見つからない。** 別のドメイン問題を同じ構造で解いて
いるので、問いと語彙を共有しない —— time window の前例は page cursor であり、「window」で検索しても届かない。
層が実際に何を含んでいるかを数え上げ、それぞれの形を見る。概念で grep しない。

**そのためにグラフがある。** Graphify はテキストではなく構造を索引しているので、問いと語を共有しない前例に
届く —— 検索が確実に失敗し、走査が失敗しない唯一のケースである。ここで何が元を取るかは `.claude/README.md`
を読み、そのうえで候補となる層を数え上げ、構造的に似て見える型から走査する:

```bash
# 候補となる前例に既に何が依存しているか —— どれだけ荷重を受けているか、呼び出し元は誰か。
node .claude/scripts/graph-affected.ts <symbol> --depth 2

# 構造的な検索。budget を上げること。既定（約 2000 トークン）はこの規模のリポジトリでは切り詰められる。
GRAPHIFY="${XDG_CACHE_HOME:-$HOME/.cache}/go-boilerplate/graphify/bin/graphify"
"$GRAPHIFY" query "<structural question>" --budget 8000
```

同型だと呼ぶ前に候補をソースで裏取りすること —— グラフのエッジが示すのは関係であって、2 つが同じ形の問題を
解いていることではない。グラフが無い、または遅れている（`graphify-out/GRAPH_REPORT.md` の
`Built from commit:` と `git rev-parse HEAD` の比較）ときはそう述べる。回せなかった構造的掃引は「前例なし」を
弱い主張にする要素だからである。

その非対称性が立証責任を決める。「見つけた」は検分で検証できるので探索範囲は要らない。「無い」は開いていない
150 のパッケージについての主張なので、どの層を数え上げたかを述べる —— そして掃引が部分的だったなら、分岐が
実在すると断ずるのではなく、*その確認が済むまでの暫定*として選択肢を提示する。

該当するときははっきりそう述べる:

> 設計分岐なし。`<X>` は既存の `<Y>` と同型で、配置・構築・呼び出し位置はそちらの前例で確定する。

評価軸に手を伸ばすのは、この工程が何も見つけなかったときである —— そして「何も見つからなかった」は勝ち取る
べき主張である。コードベースが既に決着させた設計分岐をでっち上げることこそ、この工程が防ぐために在る失敗
だからである。

## Step 2 — 評価軸を固定し、以後は触らない

*この*問いのための軸を選び、案を 1 つも名指す前に書き留める。

このリポジトリには出発点になる前例がある —— 業界的正しさ / DDD 整合性 / アーキテクチャ純粋性 / template 先の
純粋性 —— そしてそれは出発点であって固定の評価表ではない。ビルドゲートの問いに DDD の軸は無いし、語彙の
問いはほとんど DDD の軸だけである。問いが実際に何で決まるかを選び、各軸がなぜそこに在るのかを述べる。

4 つのうち最後のものが最も忘れられやすく、最もしばしば決定的である。**このリポジトリの製品は、プロジェクトが
`useTemplate` 時点で受け取る状態**であって、それを生んだ履歴ではない。このリポジトリを見たことがなく、その
git log を読むこともない人にとってどうかで各案を測る。`AGENTS.md` の *What to Recommend* 節がこれを統べる。

## Step 3 — 選択肢を数え上げる —— 数は要点ではない

問いが実際に持っている選択肢を数え上げる。3 はよくある数であって要件ではない。やる / やらない の問いは 2 つ
であり、形を埋めるために 3 つ目をでっち上げると藁人形ができ、比較を実際より入念に見せてしまう。本当に異なる
approach が 5 つあるなら 5 つになる。ほぼ重複するものを統合して圧縮するのはよいが、異なるものを落として
圧縮してはならない。

案ごとに、Step 2 で固定した軸に照らして:

| 項目 | 何を書くか |
| --- | --- |
| 案 | 「案 A」ではなく、それが何であるかを述べる名前 |
| 利点 / 欠点 | 形容詞ではなく帰結 |
| リスク | 失敗モード、移行、運用負荷、セキュリティ、ロックイン |
| 既存構造との整合 | どの層が所有するか、`docs/rules.md` のどの規則に触れるか、他に何を強いるか |
| コスト | 触るファイル、誰にとって何が壊れるか、何を再生成する必要があるか —— 述べるだけで、判定に重みとして入れない |

測っていないコストはトレードオフではなく推測である。「ホットパスに読み取りが 1 つ増える」は確認できる ——
両設計のクエリ数を数えるか、主張を落とす。blast radius も同じで、「だいたい 30 ファイル触る」はグラフが
見積もるのではなく算出する数なので、各案が変えるシンボルから逆走査し
（`node .claude/scripts/graph-affected.ts <symbol> --depth 2`）、返ってきたものを報告する。

## Step 4 — 推奨し、何があれば覆るかを述べる

**推奨を出す。** 推奨を添えずに渡された比較は、尋ねた人へ仕事を返している。このリポジトリでは、推奨は
求められてからではなく選択肢と一緒に届くことが期待されている。

そのうえで反転条件を書く —— それが違っていれば答えが変わる事実。これが、推奨を議論ではなく証拠で覆せるように
するものであり、同時に、自分が何を確信していなかったかの正直な記録でもある:

> この推奨は、`<前提>` が成り立つ限り。`<条件>` なら B が優位に転じる。

## Step 5 — この契約で答える

常にこの形、日本語で。推奨を先頭に置く。比較はその裏付けである。

````markdown
## 問題
<何を決めようとしているか、1〜2 文>

## 前提
- <置いた仮定と、それが崩れたときの影響>

## 評価軸
- <軸> — <なぜこの問いでこの軸なのか>

## 選択肢
### <案の名前>
- 利点 / 欠点 / リスク / 既存構造との整合 / コスト

## 推奨
<どれを、なぜ>

## 推奨が変わる条件
- <この事実が違えば結論が変わる>

## 決めるべきこと
- <人間が決める事項> — 記録先: ADR / issue / spec のどれか

## 出典
- <発行主体> 「<資料名>」 <URL> （参照 <日付>）
````

問いの一部しか調査できなかったときは、その部分を返し、残りを未調査として名指す。正確な部分的比較は、
完結して見える比較に勝る。

## 出典

外部の主張はすべて発行主体・資料名・URL・参照日を伴う。二次的な要約より、一次・公式の資料 —— そのプロジェクト
自身のドキュメント、仕様、リリースノート —— を優先する。

参照が使えないとき、あるいは主張を確認できないときは、**未確認だと述べ、それに依るものの確度を下げる**。
読んでいないベンチマーク値・バージョン番号・非推奨日・引用を決して作らない。ここでの出典の捏造は小さな誤りでは
ない。決定が下される瞬間には本物と区別がつかず、そのまま ADR に残る。

リポジトリ内の主張については、パスとシンボルを引用し、行番号は決して引用しない。

## 単独で成立する設計

このスキルは `決めるべきこと` を作って止まる。案を採択せず、ADR を書かず、issue を起票せず、実装を始めない ——
そして `new-issue` も `impl-issue` も代わりに起動しない。

推奨と決定の間の隙間こそがこの工程の要点である。実装へそのまま流れ込んだ推奨は誰にもレビューされていない。
`AGENTS.md` がアーキテクチャ・ドメイン・方針の決定を人間のゲートの後ろに置いているのは、コードまで生き残った
案を誰かが選んだ状態にするためである。先へ進む経路は、人間の承認、次に `new-issue`、次に `impl-issue` である。

## やること / やらないこと

- ✅ 先に現状を確定する。不明なら止まり、`repo-truth` を次の一手として名指す。
- ✅ 既に ADR / spec の決定が立っているならそれを答えとして報告する。
- ✅ `docs/adr/README.md` / `docs/design/README.md` を関心事で探す。機能の言葉では探さない。
- ✅ 設計分岐として扱う前に同型の機構を探す —— 概念を grep するのではなく、層が持つものを数え上げて形で探す。
- ✅ 前例が無いと断ずる前に、どの層を数え上げたかを述べる。掃引が部分的なら選択肢を暫定として示す。
- ✅ 構造的な前例と blast radius にはグラフを走査し、そのうえでソースで裏取りする。
- ✅ 案を 1 つも名指す前に評価軸を固定し、各軸の理由を述べる。
- ✅ このリポジトリの履歴ではなく `useTemplate` 時点の読者にとってどうかで測る。
- ✅ コストは推奨と並べて、情報としてはっきり述べる。
- ✅ 推奨をその根拠とともに、そして反転条件とともに出す。
- ✅ 外部の主張には発行主体・資料名・URL・参照日を付ける。
- ✅ 日本語で答える。
- ❌ 目標の案数に届かせるために選択肢をでっち上げる、本当に異なるものを落とす。
- ❌ 好ましい案が分かった後で軸を選ぶ。
- ❌ コストに推奨を決めさせる。
- ❌ ベンチマーク・バージョン・日付・引用を発明する。未検証の主張を検証済みとして提示する。
- ❌ キーワード検索から、あるいは数え上げていない層から「前例なし」を断ずる。
- ❌ 案を採択する、ADR を書く、issue を起票する、何かを実装する。
- ❌ 決着した決定を自分の判断で再び開く。
- ❌ `repo-truth`、`new-issue`、`impl-issue` へチェーンする。

      報告した。

- [ ] どの案も名指す前に評価軸を固定し、理由を述べた。
