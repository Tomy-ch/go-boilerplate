## 観点の優先度（重要）

このスキルの主眼は **「実装の綺麗さ」= 可読性・保守性・設計の素直さ**。ここに最も注力する。
**レイヤ越境・依存方向・命名規約・フォーマットといった機械的規約違反は lint で潰せている前提**なので、
原則として指摘しない（lint で検出可能な事項は重複指摘になる）。lint では捨えない、人間が読まないと
気づけない実装品質の問題を拾うこと。

## 検証観点（対象モジュールの実装に限定。1 を主、2〜4 を従とする）

1. **実装の綺麗さ / 保守性（主観点）**:
   - 重複・コピペ、抽象化の不足/過剰、責務が 1 箇所に詰め込まれた関数・型（凝集度の低さ）。
   - 過度な複雑性（深いネスト、長い関数、巨大 switch、不要な分岐、フラグ引数）。
   - 命名と実体の乖離、誤解を招く名前、コメントと実装の食い違い。
   - 冗長・自明なコメント。コメントに残すのは振る舞い/契約（何をするか・前提・副作用）の記述のみ。
     内部手続きの逐語的な実況や、コードを読めば自明な WHAT の繰り返しは不要。なぜ／内部でどう動くか
     （設計意図・トレードオフ・経緯）は陳腐化しやすいのでコード内に書かず README / commit message へ置く。
     ただし宣言直前の godoc（unexported 含む）は振る舞い記述として保持し、指摘対象としない。
   - デッドコード、使われない公開シンボル、不要な間接化、車輪の再発明（標準/既存ユーティリティで済む）。
   - エラーハンドリングの一貫性（握り潰し、文脈欠落、ラップ漏れ）。
   - 同モジュール内の類似処理間での実装スタイルの不統一。
   - テスト容易性を損なう構造（隠れた依存、グローバル状態、副作用の混在）。
2. **正当性（従）**: 境界条件 / null・ゼロ値 / 競合（並行・順序）/ リソースリーク /
   例外時の不変条件破れ。**バグになり得る**ものに絞る。
3. **セキュリティ（従）**: 入力検証欠如、インジェクション、機微情報の露出/ログ出力、安全でない既定値。
4. **性能（従）**: N+1、不要な全件取得、明らかな計算量の問題、ホットパスの非効率。

レイヤ違反・依存方向・責務の越境は **lint と Pass1(architecture.md) の担当**。ここでは再掲しない。
ただし lint では機械検出できない「責務配置の不自然さ（綺麗さの問題として）」は 1 に含めてよい。

**対象がコード以外（設定/SQL/Dockerfile/シェル等）の場合**は、その種別の観点で見る:

- SQL（`*.sql`）: 正当性（NULL/結合条件/ソート安定性）・インジェクション・インデックス未使用/全件走査・N+1 誘発・マイグレーションの可逆性/破壊性。
- YAML/JSON（OpenAPI ソース・compose・CI 等）: スキーマ妥当性・契約整合（重複/欠落/型）・秘匿値のハードコード・最小権限。
- Dockerfile: レイヤキャッシュ効率・ベースイメージ/依存のバージョン固定・root 実行や不要パッケージ等のセキュリティ。
- Makefile/`.mk`/シェル: 正当性・移植性（bashism/未クォート変数）・冪等性・エラーハンドリング（`set -e` 等）。
いずれも基準（{{BASIS}}）にプロジェクト規約があればそれを優先する。

**対象がテストファイル（`*_test.go` 等）の場合**は、上記に加えてテストの綺麗さも見る:
table-driven の適切さ、ケース名の説明性、`t.Parallel()` の有無、前提と検証の分離
（エラー系は `require`、終端の値検証は `assert`）、過度なモック・重複・脆いアサーション。
ただし基準（{{BASIS}}）にテスト規約が明記されていればそれに従い、無ければ一般原則のみで判断する。

生成ファイル（`*.gen.*` / `*.sql.go` / `*_mock.go` / vendor 等）は**検証対象外**。観測はするが指摘しない。

## 出力要件

- 冒頭 1 行で対象モジュールと「基準の所在」を明記。
- 各指摘は次を**必ず**含む:
  - **重大度**: Critical | High | Medium | Low
  - **ファイル:行**: 具体的な位置（範囲可）
  - **問題**: 何が起きるか / どう壊れるか
  - **根拠**: なぜ問題か（コードの観測事実 + 基準/原則）
  - **修正案**: 具体的な直し方
- 重大度の高い順。
- **問題の無いものは列挙しない。** 前置き・要約・賞賛・所感を書かない。
- **対象に指摘が1件も無い場合は、`問題なし` という1行だけを出力する**（空出力にしない。
  これは「検証済み・指摘ゼロ」を表す完了マーカーで、再開時のスキップ判定に使われる）。
- 確証が持てず検証不能な点は「検証不能（基準欠如）」と明記し、推測で断定しない。
- 日本語で出力。出力はこのユニット実装検証レポートの本文のみ（Markdown）。
