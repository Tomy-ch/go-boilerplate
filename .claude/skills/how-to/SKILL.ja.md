# How To

「ここではこれをどうやるのが正規か」に、実際に実行できる手順で答える。

## 使うとき

- 操作を実行したいが、正規の経路が分からないとき。
- コマンドの心当たりはあるが、それが正規のものか知りたいとき。
- 既にコマンドは知っているが、前提条件・成功の判定・切り戻しが要るとき。

以下には使わない: 症状や落ちたゲート（`repo-ops`）、やり方ではなく仕組みの説明（`repo-truth`）、未決の
選択肢の比較（`research`）、コード変更の実行（`impl-issue`）。

## 契約

| | |
| --- | --- |
| **所管** | 目標 → 正規手順（前提 / 成功判定 / 復旧 / 警告つき）、および所有スキルへの routing |
| **しないこと** | コマンドの発明 / 所有スキルの手順の再記述 / 破壊的操作の無断実行 / ツールの独断インストール |
| **開始条件** | 実行したい操作があり、正規経路が不明なとき |
| **停止条件** | 索引を通読しても手順が無い（UNDEFINED）、候補が複数で決着しない（AMBIGUOUS）、権限超過（BLOCKED） |

## なぜ必要か、そしてなぜ `repo-ops` ではないのか

2 つは別の入口であり、混ぜると両方が壊れる。

`repo-ops` は**症状駆動**である。何かが想定外の振る舞いをし、それを既知の落とし穴の索引に照合し、§N が
その修正になる。あれの価値は、載っているものすべてを実際に誰かが踏んでいることにある。あれは「手順が
存在しない」と結論できないし、それを教えれば沈黙が答えと区別できなくなる。

このスキルは**目標駆動**である。達成したいことは分かっていて、ここでのやり方が分からない。その問いには
索引が無い。スキルが 44、`.mk` が 52、フック設定が 1 つ、workflow ディレクトリ、`docs/maintenance/` ——
そして「X をやる正規のやり方」をそれらを横断して数え上げているものは何も無い。`tool-map` はスキルを
棚卸しし、`make help` は target を並べるが、どちらも目標には答えない。

このスキルが形作られている失敗は具体的である: **尤もらしいコマンドは、文書化されたコマンドと区別が
つかない。** `make test-integration` はまさに存在しそうな target で、書き下せば権威あるものとして読まれ、 <!-- skill-lint-ignore -->
尋ねた人がそれを実行する —— そして存在しない。この repo 自身の lint にこの文を通させるために、意図的な
非参照として印を付ける必要があったこと自体が要点である。正規のコマンドを出すか、何も出さないか、
許される結末はその 2 つだけである。

## 引数と入口の確認

| 引数 | 効果 |
| --- | --- |
| `--mode=lookup`（既定） | 手順を出す。何も実行しない |
| `--mode=run` | 操作を実行する。破壊的な各ステップは個別に確認する |
| `--dry-run` | `DRY_RUN=1` 形式を持つステップはすべてそちらを優先する |

`--mode` は利便性ではなく安全のために在る。これが無いと「実行してほしかったのか説明してほしかったのか」を
言い回しから推測することになる —— *やって*を意味する言い回しと*見せて*を意味する言い回しは助詞ひとつしか
違わない。読み取りならその推測でよいが、`make db-test-reinit` では通らない。フラグが無ければ `lookup` と
みなす。実行してほしかった人にコマンドを見せる代償はターン 1 つ、逆の代償はデータベース 1 つである。

**そのうえで、自分が正しい入口かを確認する。** 隣接するスキルは同じ名詞を取り、問い手が何を述べているかだけが
違う:

| 問い手が述べているもの | 入口 |
| --- | --- |
| 壊れたもの、落ちたゲート | `repo-ops` |
| どう動くか、規則は何か、存在するか | `repo-truth` |
| 実行したい操作 | ここ |

ここへ症状が来た場合こそ拾う価値がある。既に壊れた状態にあるシステムに対して手順を組み立てると、前提条件が
成り立たないステップができあがる。そのまま進めず、そう述べて `repo-ops` を指す。

## Step 1 — まず所有スキルへ振る

組み立てる前に、その手順を既に所有しているスキルが無いか確認する。多くはある —— 環境変数の追加は `new-env`、
コミットは `commit`、PR を開くのは `submit-pr`、Go の昇格は `go-upgrade`、層の生成は `scaffold-*` 一族、
pin の更新は `actions-pin` / `images-pin` / `tools-upgrade` / `dep-vuln-upgrade`。

あるなら、**そう述べて止まる。** 手順を導出し直さない。2 箇所に存在する手順は乖離し、腐るのはコピーの側で
ある —— これは `back-prop` が強制している README > Code > SKILL の優先順位を、手順に当てはめたものである。

```bash
ls .claude/skills/                       # 何があるか
grep -l "<goal keywords>" .claude/skills/*/SKILL.md
```

棚卸しそのものが問いなら `/tool-map` を回す。

## Step 2 — レジストリから、関心事で組み立てる

どのスキルも所有していないなら、手順は次のどれかに在る。キーワード検索ではなく**索引**を読む。target は
それが何をするかで命名されており、目標がどう言い表されたかでは命名されていない。

| レジストリ | 何を持つか | 索引 |
| --- | --- | --- |
| make target | ほぼすべての正規操作 | `.makefiles/README.md`、`make help` |
| git フック | commit / push 時に何が走るか | `.lefthook.yaml` |
| CI | PR で何が、どの env で走るか | `.github/workflows/` |
| 運用ドキュメント | ローカル構成、DB プール、昇格手順 | `docs/maintenance/` |
| 変更手順 | API / DB / ビジネスロジックのフロー | `docs/development-flow.md` |

`.claude/skills/repo-ops/SKILL.md` の §0 が、答えの対象 → 出典の正本表とノイズを除いた検索の呼び出しを
持っている。ここへ複製せず実行時に読むこと。§1-21 も、目標の問いであっても目を通す価値がある —— 手順に
付随する既知の落とし穴は 注意 に入る。

キーワード検索は最後、索引が取りこぼしたものを拾う網として。

Graphify は、checkout にあればテキスト検索の届かない構造へ届く。ここで何が元を取るかは `.claude/README.md`
に記録されている。あれが索引しているのはコードとドキュメントであって make のグラフではないので、このスキルに
とっては上のレジストリの代替ではなく補助である。

## Step 3 — 運用上の外枠を確定する

コマンドだけでは手順にならない。次のそれぞれが別の問いであり、それぞれに出典がある:

- **前提条件。** インフラの起動が要るか。DB slot が要るか（worktree なら `make slot-acquire`）。`vendor/`、
  生成物、特定のブランチが要るか。target の名前ではなくレシピを読む。
- **成功の判定。** 呼び出した側は何をもって成功と分かるのか —— 終了ステータス、変わるファイル、緑になる
  チェック。成功を認識できない手順は、成功したことにされる。
- **復旧。** 何が取り消すのか、そもそも取り消せるのか。取り消せないならはっきりそう述べる。
- **注意。** 共有状態に破壊的か、環境差があるか、遅いか、秘密情報に触るか。

このリポジトリの性質のうち 2 つが外枠を非自明にしており、毎回確認する価値がある:

- **共有インフラ。** Postgres は 1 つ（`gobp-shared`）を全 checkout が共有するので、ローカルに見える操作が
  他の worktree に影響しうる。`docs/maintenance/db-worktree-pool.md` が統べる。
- **dry-run の規約。** いくつかの target は `DRY_RUN=1` を尊重する。尊重するなら手順に入れる —— 不可逆な
  ステップを検分可能なステップに変えるからである。

## Step 4 — この契約で答える

常にこの形、日本語で。項目を省くのは本当に該当しないときだけで、そのときは黙って落とさずそう述べる。

````markdown
## 状態
FOUND | AMBIGUOUS | UNDEFINED | BLOCKED

## 手順
<何をする手順か、1 行>

## 出典
- `<path>` の `<target / 節 / job 名>`

## 前提条件
- <満たしていなければならないこと、必要な権限>

## コマンド
```bash
<正規に定義されたコマンド。存在するものだけ>
```
<UNDEFINED のときは「なし」と書き、なぜ近そうなコマンドを出さないのかを 1 行添える>

## 近いもの
- `<target / 手順>` — <ただし〜の点で目的が異なる>   ← FOUND 以外のときに書く

## 成功の判定
<どうなれば成功か>

## 復旧 / 切り戻し
<既存資料に定義されたもの。無いなら「定義なし」と書く>

## 注意
- <破壊性 / 環境差 / 共有インフラへの影響 / 未検証の点>

## 探索範囲
<通読したレジストリ / 確認した所有スキル / 検索した glob / 回さなかった掃引とその理由>
← UNDEFINED / AMBIGUOUS のときは必須

## エスカレーション
<未定義・矛盾・権限超過のとき、誰が何を決めれば進むか>
````

4 つの状態は交換可能ではない:

| 状態 | 意味 |
| --- | --- |
| `FOUND` | 正規手順が存在し、上に再現されている |
| `AMBIGUOUS` | 候補が複数あり、出典がどれが統べるかを決めていない —— 全部提示し、どれも選ばない |
| `UNDEFINED` | 所有索引を通読したうえで、正規手順が存在しない |
| `BLOCKED` | 手順は存在するが、要求された操作がここで許可された範囲を超える |

`UNDEFINED` の基準は `repo-truth` のそれと同じである。所有レジストリを**通読**し、探索範囲を添えて公表する
ことを要する。それに満たなければ状態は `AMBIGUOUS` か、答えは 確認できず であり、どの索引を読み残したかを
名指す。落とすことにコストは無い。誤った `UNDEFINED` はリポジトリについての事実として読まれる。

`UNDEFINED` のとき `コマンド` 欄には **なし** と書き、なぜ「いかにもありそうなコマンド」を出さないのかを
1 行添える。空欄にすると、次の読者が自分でコマンドを補うよう誘う —— このスキルが防ぐために存在する失敗が、
一段ずれた形で起きる。代わりに書くべきなのは惜しかったもので、`近いもの` に、目的がどの点で異なるかと
一緒に名指す。「手順が無い」とだけ告げられた読者は探しに行き、最初に見つけるのは、このスキルが既に検分して
退けたそれである。

## Step 5 — 実行する

`--mode=lookup` ではこの工程は起きない。手順そのものが成果物である。`--mode=run` なら実行する —— ただし
このフラグが認可するのは*手順*であって、その中の破壊的な各ステップではない。そちらは 1 つずつ確認する。

破壊的なことを行う前に、何を壊すのかを述べて待つ。`AGENTS.md` も `repo-ops` もこの線を引いており、理由は
共有インフラである。データベースの削除、ツリーへの `chown -R`、共有 compose プロジェクトの停止は、そのマシン上の
他のすべての checkout に届く。そして頼んだ人はたいてい自分の分だけを考えている。

自分の判断で何かをインストールしない。ツールが無いことは報告すべき findings である。`AGENTS.md` が統べており、
このリポジトリはたいてい既にその能力を `make` target の裏に備えている。

## 単独で成立する設計

このスキルは手順を渡して止まる。次に何を回すかを名指す —— 手順が既知の落とし穴で失敗したら `repo-ops`、
目標が知識の問いだったと判明したら `repo-truth`、穴が追跡に値するなら `new-issue` —— 決めるのはユーザーである。

振り先のスキルを吸収することもしない。`new-env` へ振ることが答えのすべてであり、ここで `new-env` の手順を
述べ直せば、このスキルが防ぐために存在する 2 つ目のコピーができあがる。

## やること / やらないこと

- ✅ まず所有スキルを確認し、あればそこで止まる。
- ✅ レジストリはキーワードではなく索引で読む。
- ✅ 前提条件・成功の判定・復旧・注意を、それぞれ別の問いとして確定する。
- ✅ 各ステップがどのファイルの target / 節から来たかを引用する。
- ✅ 共有インフラへの影響と `DRY_RUN=1` の可否を毎回確認する。
- ✅ `UNDEFINED` は探索範囲を添えて報告する。あるいは `AMBIGUOUS` / 確認できず へ落とす。
- ✅ `UNDEFINED` のときは `コマンド` に理由つきで `なし` と書き、`近いもの` に惜しかったものを ——
  目的がどの点で異なるかも含めて —— 名指す。
- ✅ 意図的に**回さなかった**掃引を、理由とともに記録する。
- ✅ 破壊的なことの前に警告して待つ。
- ✅ `--mode` が無ければ `lookup` として扱う。実行の認可を言い回しから推測しない。
- ✅ 日本語で答える。
- ❌ 生成物・lockfile・`.ja.md` を手で編集する、片側を選ぶ。
- ❌ 手順を所有しているスキルの手順を述べ直す。
- ❌ キーワード検索から、あるいは通読していない索引から `UNDEFINED` を報告する。
- ❌ 食い違う出典のどちらかを選ぶ —— 両方提示してエスカレーションする。
- ❌ 何を壊すか述べずに破壊的コマンドを実行する。見せるようにとだけ頼まれたコマンドを実行する。
- ❌ ツールが無いからインストールする。
