# ADR-0010: フィードバックループが観測する単位を開発の窓とする

English canonical: [0010-development-window-as-feedback-unit.md](0010-development-window-as-feedback-unit.md)

## Status

accepted

## Context

[ADR-0008](0008-agent-environment-alignment.md) はエージェント環境を閉じたループで改善すると決め、[ADR-0009](0009-long-running-agent-state.md) はその観測をどこに置いてよいかを決めた。どちらも、ループが「何を 1 つと数えるか」を述べていない。それが無いと、産出されるすべての指標が曖昧になる。「これはどれだけかかったか」に主語が無いからである。

素直な候補はセッションだが、それは誤りである。このリポジトリ自身の 30 日分の実測は次のとおり。

- セッションは 1 つの作業よりはるかに長い。中央値 3.1 h、p75 11.2 h、p90 26 h、最長 104.7 h。人は作業の切れ目で文脈を消すのであって、終了して起動し直すのではない。
- 作業ブランチをちょうど 1 本だけ触るセッションは 48% しかない。38% は 2 本以上、13% は 0 本（base ブランチ上の調査）である。
- 一方でセッションはほぼ 1 つの checkout に対応する。84% が単一の `cwd` を持つ。

つまりセッションは作業の*場所*であって、作業の*単位*ではない。セッション単位で時間を合計すると、無関係な複数のタスクが平均されてしまう。それは誰も手を打てない数字そのものである。

そこから第二の問いが出る。ループが知りたいことの一部は GitHub も記録している（PR がいつ開いたか、いつマージされたか）。ならばループはそれを読み戻すだけでよく、ローカルには何も記録しなくてよいのではないか、という結論を招く。

## Decision

**観測の単位は開発の窓とする。すなわち 1 つの作業を、手に取った瞬間から手放す瞬間まで。**窓はセッション・checkout・ブランチ・作業者で識別され、複数のセッションが 1 つの窓に属しうるし、複数の窓が 1 つの issue に属しうる。

**窓を区切るのは人の行為であって、ランタイムの都合ではない。**`/clear`、手動の `/compact`、セッション終了が窓を閉じる。自動 compact は閉じない。あれは作業の途中で文脈が埋まっただけであり、境界として扱えば長い作業を半分に切り、その両方のフェーズ時間を半減させる。両者を区別できるのは `PreCompact` イベントだけで、その payload が `trigger` を持つ。後続の `SessionStart` は両方を `compact` として報告する。ブランチの切り替えは境界ではなく傍証とする。base ブランチと feature ブランチの往復は 1 つの作業の内側で起きるからである。

**発生源で観測できる瞬間は、発生源が記録とする。**フェーズ境界は、それを跨ぐワークフローがローカルで打刻する。GitHub は相互チェックと fallback であって、出所ではない。両者は同じ事実ではない。マーカーは「ワークフローがその段階に到達した」と言い、API は「オブジェクトが作られた」と言う。PR が窓の外で開かれたとき、あるいは段階に達した後で push が失敗したとき、両者は食い違う。信頼性も等しくない。時刻を読み戻すには branch → PR の結合が要るが、実測で 64% しか成立しない。ネットワークも要るが、ループはそれ無しで動くことを要件としている。両者の不一致が記録されたなら、それはノイズではなく所見である。ゆえにすべての値が、どちらの出所から来たかを併せ持つ。

## Consequences

### Positive Consequences

- 期間が意味を持つ。「実装にどれだけかかったか」に答えられるのは、その区間に主語が 1 つだからであり、窓の中のフェーズを窓どうしで比較できる。
- ループはオフラインでも資格情報無しでも動き続ける。第一の記録が作業の起きる場所に書かれるからである。
- PR に到達しなかった作業 — 調査と、諦めた試行 — も期間を持つ窓として残る。この 2 種はこれまでこのリポジトリが全く観測できていなかったものである。

### Negative Consequences

- 境界の質は、その背後にある信号の質を超えない。文脈を一度も消さない人は 1 つの非常に長い窓を走らせ、そのフェーズ時間は相応に粗くなる。ループは観測した窓を報告するのであって、発せられなかった境界を推測しない。
- マーカーはそれを担うワークフローが書くので、そのワークフローを通らずに行われた窓は中間が欠ける。実測でコミットの 51% はコミットワークフローを経由しない。だからコミットのマーカーは git フックが打ち、残りのマーカーは欠測時にトランスクリプトからの導出値へ縮退する（無記録にはしない）。
- 同じ瞬間について 2 つの記録が食い違いうるので、その食い違いを誰かが見る必要がある。

## Alternatives Considered

### セッションを単位とする

実測により却下。セッションの 38% が 2 本以上の作業ブランチを含むため、セッション単位の時間は無関係なタスクを混ぜる。しかもこの失敗は静かである — 数字自体は計算できてしまう。最も質の悪い種類の失敗である。

### ブランチの切り替えを境界とする

却下。1 つの作業が base ブランチと feature ブランチの間を日常的に往復するため、大半の窓が少なくとも一度は割れる。人自身の信号が既に立てた境界に対する傍証としてのみ残す。

### すべての時刻を GitHub から読み戻し、何も打刻しない

却下。オフラインで失敗し、資格情報が無ければ失敗し、PR を持たない 3 分の 1 の作業ブランチでも失敗する。さらに問われているのとは別の問いに答えている。オブジェクトの作成時刻は、ワークフローがその段階に到達した瞬間ではない。

### モデルにトランスクリプトを読ませて境界を導出する

却下。境界が事実ではなく読解に依存することになる。[ADR-0008](0008-agent-environment-alignment.md) は、決定論的な根拠が存在する場面ではループの判断をそれに載せることを要求している。ここでの信号は決定論的であり、既に存在している。
