# ADR-0014: Retain the bundled openapi.gen.yaml as a committed cross-repo contract artifact

## Status

accepted

## Context

ADR-0012 (Redocly modular spec pipeline) establishes a three-stage pipeline:
**Lint → Bundle → Generate**. The bundle step produces `openapi/openapi.gen.yaml` — a
fully resolved, single-file OpenAPI document. From the server side, this file is consumed
immediately by oapi-codegen (ADR-0013, oapi-codegen strict-server) and could in principle
be discarded after the Go stubs are generated, just as other intermediate build artifacts
are.

However, `openapi.gen.yaml` is also the **only representation of the full, resolved contract
that an external consumer can parse without installing the Redocly toolchain**. The frontend
codebase generates typed HTTP client code from this file (e.g. via orval + zod) in a
separate repository. If the file is not committed, the frontend must either replicate the
Redocly bundle step itself or consume an unresolved, multi-file spec — both options add
toolchain coupling and build complexity on the consumer side.

The general project rule ("do not commit generated files") exists to avoid stale outputs
being silently trusted. This tension is resolved by the generated-artifact drift gate
(ADR-0085, generated-artifact drift gate), which fails PRs when the committed
`openapi.gen.yaml` diverges from the current sources, keeping the file perpetually fresh.

## Decision

Retain `openapi/openapi.gen.yaml` as a **committed artifact** in the repository.

The file is regenerated by `make gen-api` (the `gen-bundle-oapi` step runs
`redocly bundle openapi/openapi.yaml -o openapi/openapi.gen.yaml`) and its freshness is
enforced by the `gen-oapi-artifacts-check` CI workflow defined in the generated-artifact
drift gate (ADR-0085). The frontend pulls the committed file via the GitHub API (e.g. with
the `gh` CLI) and uses it as the source for its own code-generation pipeline (e.g. orval +
zod), without needing to run the Redocly toolchain.

The file must never be edited by hand. Its authoring source is the modular spec under
`openapi/` (ADR-0012, Redocly modular spec pipeline).

## Consequences

### Positive Consequences

- The frontend can fetch the resolved spec from any git ref via the GitHub API without
  installing Node.js or Redocly, keeping frontend build dependencies lean.
- The single-file representation is immediately parseable by any standard OpenAPI tooling
  (orval, openapi-typescript, swagger-codegen, etc.) with no further resolution step.
- The committed file serves as an auditable snapshot: reviewers can see what the published
  contract looked like at any point in git history.
- The drift gate (ADR-0085) ensures the committed file stays in sync with the modular
  sources — the "stale committed output" risk that normally discourages committing generated
  files is mechanically eliminated by CI.

### Negative Consequences

- Every OpenAPI source change requires a `make gen-api` step before committing; forgetting
  triggers a CI drift-gate failure, adding a mandatory discipline step for contributors.
- The committed file is larger than the modular sources; it inflates repository size and
  produces noisy diffs in PRs that touch many schema files.
- Hand-editing `openapi.gen.yaml` is forbidden but not technically blocked by repository
  tooling; contributors must be aware of this constraint through convention.

## Alternatives Considered

### Discard after generation; frontend replicates the bundle step

The frontend CI installs Redocly and runs `redocly bundle` against the modular sources
(checked out as a submodule or fetched via the API). Rejected because it forces the
frontend to take on the Redocly toolchain as a build dependency and to understand the
server's modular `$ref` structure — tight coupling across repository boundaries.

### Publish via GitHub Releases or Packages

The bundled YAML is attached to a GitHub Release or published as a package artifact on
each release. Rejected for the day-to-day development flow because the frontend would
receive updates only at release cadence, not at every merged PR. Mid-sprint API changes
would be invisible to frontend developers until a release is cut.

### Serve the spec from a running server endpoint

The server exposes the resolved spec at a runtime endpoint (e.g. `/openapi.yaml`); the
frontend fetches it from a deployed environment. Rejected because it introduces an
environment dependency into the frontend build pipeline and makes spec access contingent
on a running server.
