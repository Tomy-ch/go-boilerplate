# ADR-0027: 絞り込みと並びを持つ一覧クエリには、プランナが実際に通る経路に沿ったインデックスを張る

English canonical: [0027-list-query-access-path-index.md](../../adr/0027-list-query-access-path-index.md)

## ステータス

accepted

## 背景

行を絞り込み、並べ替え、先頭 `limit` 件だけを返す一覧エンドポイントは、本プロジェクトに繰り返し現れる形である。
要求される並び順にキー順が一致するインデックスが無いと、データベースは該当行をすべて読み、集合全体をソートし、
先頭ページ以外を捨てる。`LIMIT` は何も打ち切れないため、応答時間はページではなくテーブルとともに増大する。

インデックスを足せば直る、というわけではない。インデックスがソートを取り除けるのは、プランナが
**要求された順序でインデックスを歩きながら絞り込みを適用できる**ときだけであり、それが可能かどうかは、
どの列にインデックスを張ったかだけでなく、絞り込みがどう表現されているかに依存する。本リポジトリの
2 つの事例が、その違いを具体的に示している。

- 同一行の 2 列を比較する絞り込み（`quantity <= stock_warning_threshold`）は、決してインデックスキーに
  できない。インデックスが保持するのは列の値であって、値どうしの関係ではないからである。ただし、
  要求された並び順のインデックスを歩きながら残余条件として評価することはできる。
- 結合先のテーブルに対して表現された絞り込み（`purchase_statuses.code = ?`）は、ローカルの外部キー列の
  単一の値に解決されるが、プランナがその値を順序付きのインデックス条件として使う義務は無い。代わりに
  ビットマップスキャンを選ぶことがあり、その場合インデックスの順序は失われ、該当行すべてに対する
  ソートが復活する。

後者こそが素朴な規則を危険にする。インデックスは存在し、プランからシーケンシャルスキャンは消え、
それでいてクエリは少しも速くならない。ビットマップスキャンが top-N ソートの前に該当行をすべて
実体化するからである。テーブルは何も得ないままインデックスの書き込みコストを払うことになる。

## 決定

絞り込みと並びを持つ一覧クエリにインデックスを足すのは、**代表的な規模での `EXPLAIN` がプランの変化を
示したときだけ**とする。具体的には、ソートノードが消え、走査が `LIMIT` で早期に打ち切られること。

インデックスのキー順はクエリの `ORDER BY` と一致していなければならない。インデックスキーにできない述語
（列同士の比較）は残余条件のまま残す。そもそもインデックスに入れる価値のある行を絞るだけの述語
（NULL 許容の設定列）はインデックスの `WHERE` 句にし、インデックスが運用上意味のある部分集合だけを
保持するようにする。

**プランを変えないインデックスは、「後で効くかもしれない」として残さず却下する。** そのコストは
現実かつ継続的で（インデックス列への書き込みのたびに保守が発生する）、一方で便益はクエリが書き換え
られるまでゼロである。インデックスが効かない原因がクエリの**形**にあると測定が示した場合、その形を
変えるかどうかはクエリについての別の決定であって、効かないインデックスを併存させ続ける理由にはならない。

本決定が扱うのは物理的なアクセス経路だけである。クエリが何を返すか、ドメイン規則が SQL でどう
表現されるかを変えることを認めるものではない。

## 影響

### 正の影響

- 対象となる一覧クエリのコストが、走査するテーブルではなく返すページに比例する。インデックスは要求
  された順序で歩かれ、`LIMIT` 件が揃った時点で打ち切られる
- 部分インデックスはテーブルではなく運用上意味のある部分集合の大きさになるため、少数の行にしか設定
  されない列のために全件インデックスを払わずに済む
- 効かないインデックスを却下することで、何も買わない保守を書き込み経路に持ち込まずに済み、本当の
  障害が「対処済みに見える」状態に隠れずに残る

### 負の影響

- アプリケーションが更新する列にインデックスを張ると、その列への書き込みが高くつき、行は heap-only
  update の対象から外れる。インデックス対象の列が、まさに書き込みエンドポイントが変更するために存在
  する列である場合、これは読み取り（ときどきしか起きないかもしれない）のために書き込み経路
  （多くの場合こちらが忙しい）へコストを移す取引になる
- 残余述語はインデックス探索のあとに行ごとに評価されるため、並び順のインデックスであっても一致しない
  行を読んでは捨てる。一致が希少なとき、1 ページを埋めるのにインデックスの大部分を歩くことがある
- クエリの `ORDER BY` とインデックスのキー順の対応は機械検査されない。クエリの並びを変えるとソートが
  黙って復活し、テストは緑のまま性能だけが退行する
- インデックスごとにストレージと vacuum / analyze の対象が増える。当該エンドポイントを一度も呼ばない
  fork は便益なしにこれを払う。そうした fork は自前のマイグレーションで削除できる

## 検討した代替案

### 絞り込みのある一覧クエリすべてに原則としてインデックスを張る

一様で測定を要しない。却下: プランを変えないインデックス、すなわち純粋なコストを生む。2 つの事例を
分けるのは測定そのものなので、これを省略することはできない。

### 何もインデックスを張らず、物理設計を利用側プロジェクトに委ねる

正しいインデックスはデータ量と書き込み比率に依存し、それを知るのは利用側だけなので、ボイラープレート
としては筋が通る。却下: 絞り込み軸にインデックスを持たない一覧クエリは規模によらず誤った手本であり、
読者は「決めていない」と「意図して張っていない」を区別できない。

### カバリング列（`INCLUDE`）を足して残余述語をインデックス内で評価する

捨てられる行の heap fetch を減らせる。却下: 書き込み経路が既に更新している列に対してインデックス
エントリの幅を広げることになり、本 ADR が主たる取引と見なす書き込み側のコストを深める。また部分述語
による絞り込みが既に効いているため、残る利得は小さい。

### 述語を式インデックスとして書き換える

列同士の比較は、差分に対する式として書き換えればインデックス可能になる。却下: クエリの並びが式の順序に
変わり、エンドポイントが規定する結果とは別物になる。さらに、ドメイン規則の SQL 形を、それを定義する
ドメインメソッドから引き離してしまう。

### 述語を生成列として実体化し、それにインデックスを張る

絞り込みと並びの両方をインデックスで満たせる。却下: 生成モデル・ドメインエンティティ・API 契約にまで
波及するスキーマ変更であり、アクセス経路が要求するものよりはるかに大きな変更になる。
