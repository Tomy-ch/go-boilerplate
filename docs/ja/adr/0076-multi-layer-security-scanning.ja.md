# ADR-0076: 多層セキュリティスキャン（到達可能性フィルタ付き govulncheck + スケジュール CodeQL SAST + シークレット + FS スキャン）

English canonical: [0076-multi-layer-security-scanning.md](../../adr/0076-multi-layer-security-scanning.md)

## ステータス

accepted

## 背景

Go ウェブサービスにはそれぞれ異なるスキャンアプローチを必要とする複数の独立した攻撃面がある:

- **依存関係の既知 CVE**: 従来の依存関係スキャナーは、アプリケーションが実際に実行しないコードパスに
  あるものを含め、推移的にインポートされたすべてのモジュールのすべての CVE を報告する。
  これによりスキャナーへの信頼を損なう高い偽陽性率が生じる。
- **ロジックレベルのセキュリティバグ**: SQL インジェクション、パストラバーサル、安全でないデシリアライズ、
  および類似のパターンは依存関係バージョンチェックでは検出できない。ソースコードの意味解析が必要である。
- **漏洩したシークレット**: リポジトリに誤ってコミットされた API キー、パスワード、秘密鍵は
  異なる検出器（意味論的ではなくパターンベース）が必要である。
- **依存関係の脆弱性の広さ**: 到達不能なコードを含む完全な依存関係ツリーをカバーする 2 番目のスキャンが、
  優先順位付けとアドバイザリ追跡のより広いセーフティネットを提供する。

4 つの攻撃面のすべてを単一のツールで適切にカバーすることはできない。目的に合ったツールを使用した
層状アプローチが必要である。

## 決定

それぞれ独自のトリガースケジュールとツールを持つ 4 つの独立したセキュリティスキャン層を運用する:

**1. 到達可能性フィルタ付き脆弱性スキャン — govulncheck**（`vulnerability-check.yaml`）:
`.go`、`go.mod`、または `go.sum` に触れるすべての PR でトリガーされる。`govulncheck -json ./...`（JSON モード）を実行し、
出力を `jq` で後処理してコールトレース深度が 1 より大きい（つまり脆弱なシンボルがアプリケーションのコールグラフから
実際に到達可能な）発見のみを保持する。到達不能な CVE は実行可能な発見数から除外される。到達可能な発見数は
優先度付けのため upsert PR コメントとして提示される。このスキャンは **advisory**（助言的）であり、発見時にビルドを
ハードに落とすのではなく PR 上で報告する（fail-closed するシークレットスキャンとは対照的）。

**2. SAST — CodeQL**（`code-ql.yaml`、21〜22 行目）:
Go ファイルに触れる PR、`release/*`・`develop`・`staging`・`production` ブランチへのプッシュ、
および週次スケジュール（`cron: '0 0 * * 1'`）でトリガーされる。Go 言語パックで GitHub の CodeQL エンジンを使用し、
意味解析を行ってロジックレベルの脆弱性を検出する。結果は SARIF として GitHub Security にアップロードされる。

**3. シークレットスキャン — gitleaks**（`secret-scan.yaml`）:
パス制限なし（シークレットはあらゆるファイルタイプに現れ得る）ですべての PR でトリガーされる。
Docker ベースの `go_tool_runner` 経由で gitleaks を実行し、結果を upsert PR コメントとして投稿する。
gitleaks がマッチを発見した場合は非ゼロで終了する。

**4. ファイルシステム依存関係スキャン — Trivy**（`trivy-fs.yaml`）:
`.go`、`go.mod`、または `go.sum` に触れる PR、および週次スケジュール（`cron: '0 0 * * 1'`）でトリガーされる。
`CRITICAL`、`HIGH`、`MEDIUM` の重大度で修正済みの脆弱性のみを対象として `library` 脆弱性の `vuln` スキャン
モードで `trivy fs` を実行する。Markdown サマリー（PR コメントとして投稿）と、CodeQL アップロードアクション経由で
GitHub Security にアップロードされる SARIF レポートの両方を生成する。

## 影響

### ポジティブな影響

- govulncheck の到達可能性フィルタがノイズを削減する。アプリケーションが実際に呼び出すコードの脆弱性のみが
  ブロッキングとしてフラグ立てされる。
- CodeQL はバージョンベースのスキャナーが完全に見逃すロジックレベルのバグをカバーする。
- CodeQL と Trivy の週次スケジュールは、コードの変更なしでも現在のコードベースに対して新たに公開された
  CVE を検出する。
- 別々の面をスキャンする個別のツールにより、一つの層の失敗が独立して対処可能になる。

### ネガティブな影響

- 4 つの別々のワークフローが CI の複雑さとメンテナンスする表面積を増加させる。
- govulncheck の到達可能性解析は Go モジュールの認識を必要とする。モジュールグラフが構造を変えると、
  フィルタリングの前提を見直す必要があるかもしれない。
- シークレットスキャンはすべての PR で無条件に実行され（パスフィルターなし）、すべての PR ワークフローに
  固定のオーバーヘッドを加える。
- CodeQL の週次 cron スケジュールの実行は、オープンな PR に関連していない発見を生成することがあり、
  メンテナーが積極的にトリアージする必要がある。

## 検討した代替案

### 単一の依存関係スキャナーのみ（例: Dependabot）

Dependabot は反応的に依存関係を更新するが、到達可能性解析や SAST を実行しない。ロジックレベルのバグを
完全に見逃す。

### 到達可能性フィルタなしの govulncheck

`trace > 1` の後処理フィルターなしで govulncheck を実行すると、実行されないコードパスに対する
アドバイザリレベルの発見が大量に生成される。PR 作成者は habitualy に govulncheck のすべての出力を
無視するようになり、シグナルが破壊される。

### すべてのスキャンを単一の Trivy ステップに統合する

Trivy は CVE とシークレットの両方をスキャンできるが、その意味解析は CodeQL に相当せず、
到達可能性の認識は govulncheck より弱い。統合はシンプルさのために深みを犠牲にする。

  `.github/workflows/trivy-fs.yaml`。
