# Repo Truth

リポジトリ自身の一次資料から、現在このリポジトリで何が真かを、検証できる推論過程とともに
回答します。

このファイルは人間向けの参照訳であり、スキルとしては読み込まれません。

## 使用する場面

次のような問いに使います。

- 振る舞いがどこに実装されているか、またはリポジトリ内の経路がどう動くか
- ある関心事をどの規則、規約、正本文書が統べるか
- なぜその設計になっているか
- リポジトリ固有の用語が何を意味するか
- 規則、手順、用語、実装が存在するか

リポジトリ固有の答えを持たない一般的なプログラミングやライブラリの問い、`repo-ops` に
文書化された既知の運用障害、`research` が必要な未決の選択、差分レビュー（`impl-review`、
`test-review`、`comment-sweep`）、発見事項の起票（`new-issue`）には使いません。

## 契約

| | |
| --- | --- |
| **所有するもの** | リポジトリの現状に関する事実回答、事実と推論の分離、未定義 / 確認できず の判定 |
| **決して行わないこと** | リポジトリ外の一般論を主根拠にした将来設計、未決事項の採択、変更、検出した drift の修復 |
| **開始条件** | 現状、規約、根拠、語義、存在有無を問われたとき |
| **停止条件** | 権威を持つ二つの出典が矛盾したときは矛盾を提示して停止する。所有索引を通読せず断定を求められたときは断定せず確認できずとする |

## このスキルが存在する理由

リポジトリについて記憶から答えてはいけません。レイヤ規則、target の振る舞い、レスポンス
ステータス、パッケージ責務は最後に見たときから変わり得ます。自信に満ちた近似回答は事実として
利用されてしまいます。

正本を特定することは、検索ヒットを読むこととは別の作業です。このリポジトリには除外後でも
canonical な Markdown が 518 件あり、そのうち ADR が 110 件、パッケージ README が 150 件です。
さらに `.mk` が 52 件あります。一方、権威として扱ってはならない `*.ja.md` の対訳が 495 件、
生成コピーが 144 件あります。部分的なキーワード掃引で不在を確定するには大きすぎる文書群です。

さらに `AGENTS.md` は、文書が所有する関心事によって命名されると定めています。問いを統べる
ファイル名に、問いの語が一つも含まれないことは普通です。したがって grep では答えの不在を
確定できません。ヒットがないことは規則がないことではありません。不在の主張を反証可能にする
ため、実際に探索した frontier を公表します。

根拠と推論を分けます。これは形式的な不確実性表現ではなく、読者が推論を明示的な規定と混同せず
差し替えられるようにするためです。

## 引数と入口確認

開始前の確認は求めません。次の引数から振る舞いを決めます。

| 引数 | 効果 |
| --- | --- |
| `--depth=quick` *（既定）* | 関心事を所有する索引を拾い読みする。`未定義` は使用不可で、見つからない答えは `確認できず` とだけ報告する |
| `--depth=full` | 所有索引を通読し、該当する README 連鎖を辿る。これにより `未定義` を報告できる |
| `--kind=<kind>` | 呼び出し元の分類を受け入れ、Step 1 の分類を省略する |

答えが存在しないことに依存すると判明したら `quick` から `full` へ自律的に上げ、そのことを
明記します。権威ある不在判定には所有索引の通読が必要であり、そのコストは意図的です。

探索前に入口が正しいか確認します。

| 意図 | 入口 |
| --- | --- |
| 既知の操作または gate が失敗した | `repo-ops` |
| 操作を実行したい | `how-to` |
| 設計案のいずれを採るか誰も決めていない | `research` |
| リポジトリの仕組み、規則、存在有無を知りたい | このスキル |
| 文面から複数の意味が成立する | `question` |

別の入口が所有する場合は一文でその旨と適切な入口を示します。対話セッションで曖昧さを解消する
必要があれば、通常の会話本文に短い番号付き選択肢を出し、ユーザーの返答を待ちます。Claude 固有の
モーダルやツール API には言及しません。

`how-to` と `research` という入口名は authoritative な workflow 契約に由来しますが、Codex 側の
`.codex/skills/` にはまだ存在しない可能性があります。入口が使えない場合は Codex 側 handoff の欠落を
報告し、呼び出したふりをしたり、その責務をこのスキルへ取り込んだりしません。

Graphify の広い発火条件はこの振り分けに優先しません。Graphify は Step 2 で使う探索手段の一つです。
グラフ結果だけでは根拠と推論を分けられず、frontier も公表できず、`未定義` と `確認できず` も
区別できません。

## Step 1 — 問いを分類する

分類によって正本の文書群と不在の意味が決まるため、探索前に分類します。

| 種別 | 主な回答元 | 不在の意味 |
| --- | --- | --- |
| Fact | リクエスト経路上の実装 | 経路が存在しない。ありそうな経路で代用しない |
| Rule | 統治文書 | 規則が未定義の可能性があるが、所有索引を尽くした後に限る |
| Rationale | `docs/adr/`、`docs/design/` | 決定が記録されていない可能性がある |
| Procedure | `.makefiles/**`、`.lefthook.yaml`、`.github/workflows/`、`docs/maintenance/` | 正規手順がない可能性がある。発明しない |
| Vocabulary | `docs/spec/glossary.md`、`docs/spec/<feature>/` | 未登録か、業務用語ではない可能性がある |
| History | `git log`、merge 済み pull request | 到達できる履歴を報告する |

表面的な語彙で種別を決めません。たとえば integration test の実行方法は Procedure、DB slot が
必要な理由は Rationale であり、探索する文書群が異なります。

## Step 2 — 探索 frontier を定め、出典を特定する

結論を出す前に予定する frontier を記録します。通読した索引、辿った README 連鎖、検索した glob、
実行した構造探索、未探索の関連領域を追跡します。

### 所有する関心事から索引を先に探す

問いの単語がタイトルに含まれるかではなく、各項目が所有する関心事から索引を選びます。

| 索引または連鎖 | 対象 |
| --- | --- |
| `docs/adr/README.md` | 110 件の ADR に記録された理由と棄却案 |
| `docs/design/README.md` | サブシステムと横断的設計 |
| `.makefiles/README.md` | 関心事ごとに分類された全 make target |
| 対象パスから layer root までの README 連鎖 | パッケージ責務、禁止事項、設計意図 |
| `docs/spec/glossary.md`、`docs/spec/<feature>/` | 業務語彙と feature の振る舞い |

実行時に `.codex/skills/repo-ops/SKILL.md` の §0 **Finding the authoritative source** を読みます。
ここが回答対象から出典への正本対応表とノイズ除外検索の正本であり、ここには複製しません。
Codex 側の `repo-ops` は、`Contract`、索引の所有スキル列、最新の §21、§99 採番を含む Claude 正本の
最新版より遅れている可能性があります。依拠するときはこの可能性を明記し、Codex 側にない新しい
内容が存在しないとは推論しません。

キーワード検索は所有索引の後、最後の網としてのみ使います。`*.ja.md` は決して読みません。対訳への
ヒットは英語の隣接正本を特定する手掛かりにはなりますが、読む・引用するのは英語正本だけです。
`docs/portal/**`、`docs/godoc/**`、`docs/db-schema/**`、`docs/openapi/**`、`docs/coverage/**` などの
生成ツリーは権威および広域検索から除外します。

### 二つの不在判定を使い分ける

| 判定 | 必要な frontier |
| --- | --- |
| **未定義** — 統治する規則または手順が存在しない | 関心事を所有する全索引の通読と該当 README 連鎖の踏破 |
| **確認できず** — この実行では確定できなかった | それより小さい frontier すべて |

`確認できず` は常に安全です。部分検索、キーワードの不発、quick 実行を `未定義` に格上げしません。
誤った権威ある不在判定は、後続作業がその上に積まれるため、無回答より悪い結果です。

出典が食い違う場合は `AGENTS.md` の優先順位、`AGENTS.md` → `docs/rules.md` →
`docs/architecture.md` → ユーザー指示を適用します。設計意図と実装方針では **README > Code > SKILL**
です。ただし優先順位を使って食い違いを隠さず、矛盾そのものを報告します。

### 構造的な到達関係には Graphify を使う

caller、影響範囲、「これをしているのは X だけ」のような scope 主張など、テキストより構造が
答える問いにはリポジトリグラフを使います。リポジトリでの実測知見は Claude 環境の
`.claude/README.md` にあります。その実測はリポジトリについてのもので、agent 環境に依存しません。

```bash
# Resolve a symbol and reverse-traverse callers / affected nodes.
node .claude/scripts/graph-affected.ts <symbol> --depth 2

# Structural natural-language lookup; raise the budget to avoid default truncation.
GRAPHIFY="${XDG_CACHE_HOME:-$HOME/.cache}/go-boilerplate/graphify/bin/graphify"
"$GRAPHIFY" query "<question>" --budget 8000
```

網羅的な scope の根拠には `graph-affected.ts` を優先します。node 候補を解決し、関係と source location を
報告します。重要性の代用に `god-nodes` を使いません。このリポジトリの test 1:1 対応により、edge の
多い test scaffolding が順位を占めるためです。

次の guardrail をすべて適用します。

- graph node、edge、生成 summary は根拠への到達手段であり、根拠そのものではありません。特定された
  source file を開いて引用します。
- Graphify を使ったときは必ず `graphify-out/GRAPH_REPORT.md` の `Built from commit:` と
  `git rev-parse HEAD` を比較し、双方の鮮度を報告します。
- graph は未 commit の変更を認識しません。このスキルは read-only なので、その部分には網羅的な直接検索を
  使い、graph が stale であると報告します。`make graphify-update` による再構築は次の action 候補として
  示すだけにし、ここでは実行しません。
- Graphify の出力は gitignore 対象かつ machine-local なので、存在しないことがあります。索引、source の
  直接読解、検索、履歴へ fallback し、実行できなかった構造掃引を frontier に記録します。
- 既定の query budget では関連結果が切れることがあります。増やすか、切り捨てを明示的に扱います。

## Step 3 — 一次資料を読み、境界を示す

引用する source はすべて開きます。発見しただけで開いていない path は根拠ではありません。

二つの集合を明確に分けます。

- **根拠:** code が表す振る舞い、または統治する source に実際に書かれた記述
- **推論:** 複数 source を組み合わせた結論、不在からの推定、兄弟実装との類推

推論は有用ですが推論と明示します。scope の記述は不在主張なので、Graphify の逆向き探索または別の
網羅的検索で支えます。そうでなければ実際の frontier に合わせて主張を狭めます。

## Step 4 — 鮮度と矛盾を確認する

- 鮮度が回答を左右する場合、`git log --oneline -10 -- <paths>` で判断元 path の直近履歴を確認します。
- 権威ある二つの source が矛盾するときは、双方と鮮度を報告して停止します。ユーザーに代わって方針を
  選びません。
- README と code の不一致は drift とします。README が統治し、code が発見事項です。このスキルでは
  どちらも修復しません。調整は `back-prop` が所有します。
- skill 本文は navigation であり、README や統治文書を上書きする権威ではありません。

## Step 5 — 日本語の回答契約を出力する

常に次の全 section を日本語で出力し、`回答` は 1〜3 文にします。

```markdown
## 回答
<結論を 1〜3 文で>

## 根拠
- <主張> — `<path>` の `<symbol / target / 節>`

## 推論
- <根拠から導いた内容。事実と異なる表現で>

## 矛盾 / 欠落
- <矛盾する出典と鮮度> / <未定義または確認できず> / <古い可能性>
- 探索範囲: <通読した索引 / README 連鎖 / 検索 glob / 構造探索>

## 確度
High | Medium | Low — <根拠>

## 次にできること
<追加確認 / research / new-issue / ADR 化 / back-prop など。ここでは実行しない>
```

path と、安定した symbol、target、section 名を引用します。refactor で古くなる line number は引用しません。

確度は source から判断します。

| Level | 使用条件 |
| --- | --- |
| High | 複数の現在の一次資料が一致し、問いを統治する |
| Medium | 一つの一次資料、暗黙の source、または鮮度未確認 |
| Low | 主に推論、source の矛盾、または判断元に到達できない |

問いの一部だけ検証できた場合は、その部分を答え、残りを欠落として示します。

## 欠落も回答である

正規手順がないことは結果であり、もっともらしい command を発明する理由ではありません。不在を反証可能に
する frontier とともに報告します。例:

> 正規手順は**未定義**。`.makefiles/README.md` と `docs/maintenance/` の所有索引を通読し、
> `.lefthook.yaml` と `.github/workflows/` を確認したが該当なし。近いのは `<target>` だが、
> `<difference>` のため目的が異なる。

所有索引に未読が一つでもあれば `確認できず` とし、未探索箇所を示します。`repo-ops` は既知症状の
lookup であり、どちらの不在判定も所有しません。index にない症状はこのスキルへ戻します。

## 単独で完結する設計

後続スキルを実行しません。未決設計には `research`、発見事項の起票には `new-issue`、drift には
`back-prop`、既知症状には `repo-ops` という次の候補だけを報告し、実行するかはユーザーに委ねます。

## Do / Do NOT

- 正しい入口でなければ別の入口へ振り分けます。
- キーワード検索より先に、関心事を所有する索引を探します。
- frontier を公表し、`未定義` と `確認できず` を区別します。
- 引用する source はすべて開き、安定した symbol、target、section を引用します。
- 根拠と推論を分けます。
- 矛盾は双方の source と鮮度を付けて報告します。
- 構造と scope の問いには Graphify を使い、source で裏取りし、graph の鮮度を示します。
- 日本語で回答します。
- リポジトリが決める振る舞いを記憶から答えません。
- `*.ja.md` や生成文書を権威として読み、引用しません。
- code を統治文書より、skill を README より上位の権威として扱いません。
- 権威の矛盾を解決せず、drift を修復せず、何も編集しません。
- 部分検索やキーワード検索だけから `未定義` を報告しません。
- 欠落を埋めるために規則、command、理由、path を発明しません。
- 部分検索から網羅的 scope を主張しません。
- 回答に line number を使いません。
