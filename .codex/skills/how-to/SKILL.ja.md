# How To

「ここではこれをどうやるのが正規か」に、実際に実行できる手順で答えます。

このディレクトリの `SKILL.ja.md` は、人間が参照するための日本語訳です。スキルとしては
読み込まれません。

## 使用する場面

- 操作を実行したいが、正規の経路が分からないときに使用します。
- 心当たりのあるコマンドが正規のものか確認したいときに使用します。
- コマンドは分かっていても、その前提条件、成功の判定、復旧方法、注意事項が必要なときに
  使用します。

症状や失敗したゲートには `repo-ops`、仕組みの説明には `repo-truth`、選択が未決の比較には
`research`、コード変更の実行には `impl-issue` を使用し、このスキルは使用しません。名前を挙げた
隣接スキルが `.codex/skills/` に存在しない場合は、振り分けを完了できなかったと伝え、その責務を
このスキルへ取り込まないでください。

## 契約

| | |
| --- | --- |
| **責務** | 目標から、前提 / 成功判定 / 復旧 / 警告を含む正規手順を特定し、所有スキルへ振り分けること |
| **禁止事項** | コマンドの発明 / 所有スキルの手順の再記述 / 破壊的操作の無断実行 / ツールの独断インストール |
| **開始条件** | 実行したい操作があり、このリポジトリでの正規経路が不明なとき |
| **停止条件** | 所有索引を通読しても手順がない（UNDEFINED）、候補を決着できない（AMBIGUOUS）、権限を超える（BLOCKED） |

## このスキルが存在する理由と `repo-ops` ではない理由

2 つの入口を分けてください。

`repo-ops` は症状駆動です。予期しない挙動を、整理済みの既知の運用障害一覧と照合します。
そこに記載がないことから、正規手順が存在しないとは証明できません。

このスキルは目標駆動です。望む結果は分かっているものの、このリポジトリ固有の経路が分からない
場合に使用します。その答えは、スキル、make target、フック、ワークフロー、保守文書に分散している
ことがあります。`tool-map` はスキルを棚卸しし、`make help` は target を棚卸ししますが、どちらか
一方だけでは運用目標を完全な手順へ対応付けられません。

防ぐべき中心的な失敗は、もっともらしいコマンドが文書化済みのコマンドとまったく同じように見える
ことです。たとえば `make test-integration` は正規らしく見えますが、ここでは意図的な非参照であり、 <!-- skill-lint-ignore -->
その target が存在する根拠ではありません。出典のある正規コマンドを提示するか、コマンドを何も
提示しないかのどちらかにしてください。欠けた根拠を推測で埋めてはいけません。

## 引数と入口の確認

| 引数 | 効果 |
| --- | --- |
| `--mode=lookup`（既定） | 手順を返し、何も実行しない |
| `--mode=run` | 破壊的な各ステップを個別に確認しながら手順を実行する |
| `--dry-run` | 明示的に対応している各ステップでは `DRY_RUN=1` 形式を優先する |

`--mode` は利便性ではなく安全の境界です。指定がなければ必ず `lookup` を選び、表現から実行許可を
推測してはいけません。実行してほしかった人にコマンドを見せる代償は追加の 1 ターンです。説明を
求めた人のためにコマンドを実行する代償は、データベース 1 つになり得ます。

続いて、この入口が正しいか確認します。

| ユーザーが述べていること | 振り分け先 |
| --- | --- |
| 症状、壊れた挙動、失敗したゲート | `repo-ops` |
| 仕組み、規則の内容、存在の有無 | `repo-truth` |
| 実行したい操作 | このスキルを続行 |

すでに壊れていることが分かっているシステムに通常の手順を組み立ててはいけません。前提条件が成立
していない可能性があります。その場合は `repo-ops` へ振り分けてください。

## ステップ 1 — 最初に所有スキルへ振り分ける

手順を組み立てる前に `.codex/skills/` を調べます。特に次の所有関係があります。

- 環境変数の追加は `new-env` が所有します。
- コミットは `commit` が所有します。
- Pull Request の作成または更新は `submit-pr` が所有します。
- Go のアップグレードは `go-upgrade` が所有します。
- アーキテクチャ各層の生成は、該当する `scaffold-*` スキルが所有します。
- pin と脆弱な依存関係の更新は、該当する `actions-pin`、`images-pin`、`tools-upgrade`、または
  `dep-vuln-upgrade` が所有します。

手順を所有するスキルがある場合は、その名前を挙げて停止します。振り分けが答えのすべてです。
その手順を再記述してはいけません。重複した手順は乖離し、コピーされた側が腐ります。

Claude 固有のスキル探索コマンドではなく、Codex 側の一覧を使用します。

```bash
ls .codex/skills/
rg -l "<goal keywords>" .codex/skills/*/SKILL.md
```

一覧そのものが問いである場合は `tool-map` スキルを実行します。

同期中は Codex 側のスキルのコピーが Claude 側の正本より遅れていることがあります。参照先の
`.codex/skills/<name>/SKILL.md` が存在しない、または内容が古いという具体的な根拠がある場合は、
その制約を伝えて停止します。`.claude/skills/<name>/SKILL.md` を黙って代用したり、所有スキルの
手順を再構成したりしてはいけません。`sync-ai` を実行するかは人間が判断します。

## ステップ 2 — 関心事ごとにレジストリから組み立てる

目標を所有するスキルがなければ、キーワード検索より先に、関連するレジストリの索引を全文読みます。
target はユーザーの表現ではなく、その target が行うことに基づいて命名されているためです。

| レジストリ | 所有するもの | 索引 |
| --- | --- | --- |
| Make target | 正規のリポジトリ操作の大部分 | `.makefiles/README.md`、`make help` |
| Git フック | コミット時と push 時の検査 | `.lefthook.yaml` |
| CI | Pull Request の job とその環境 | `.github/workflows/` |
| 運用文書 | ローカルトポロジー、DB プール、アップグレード手順 | `docs/maintenance/` |
| 変更手順 | API、DB、ビジネスロジックのフロー | `docs/development-flow.md` |

実行時に `.codex/skills/repo-ops/SKILL.md` のセクション 0 を読み、回答対象から出典への表と、
ノイズを減らした検索方法を確認します。その表をここへコピーしてはいけません。手順に付随する
既知の落とし穴は `注意` に含める必要があるため、同スキルの既知の落とし穴の節も調べます。

同期中は Codex 側の `repo-ops` が Claude 側の正本より遅れていることがあります。期待した節や根拠が
なければ、同等だと仮定せず、その制約を開示します。

キーワード検索は最後に、索引から漏れたものを拾う網としてのみ使用します。

Graphify の出力がある場合は、構造上の関係を補う目的にのみ使用します。Claude 環境の README
`.claude/README.md` にあるリポジトリ固有の観測結果は、このリポジトリについての事実として参照
できます。ただし Graphify はコードと文書を索引化するもので make graph は対象外なので、上記の
レジストリを置き換えるものではありません。

## ステップ 3 — 運用上の周辺条件を確立する

コマンドだけでは手順になりません。次の各項目を、それぞれ出典から独立して確立します。

- **前提条件:** 必要なインフラ、worktree の DB slot（`make slot-acquire`）、生成済み artifact、
  `vendor/`、branch の状態、認証情報、権限を確認します。名前だけでなく recipe を読みます。
- **期待される結果:** 終了 status、変更される artifact、観測可能な状態、または green になる検査を
  確認します。
- **復旧:** 文書化された取り消し手順と、復旧が可能かを確認します。復旧が定義されていなければ
  `定義なし` とし、発明してはいけません。
- **注意:** 破壊的または共有状態への影響、環境依存性、所要時間、secret、未検証の仮定を確認します。

次のリポジトリ固有の点を毎回確認します。

- 1 つの Postgres service（`gobp-shared`）を複数の checkout が共有しています。ローカルに見える
  コマンドでも、別の worktree へ影響することがあります。トポロジーは
  `docs/maintenance/db-worktree-pool.md` が規定します。
- 一部の target は `DRY_RUN=1` へ明示的に対応しています。その target または所有文書に対応が
  記載されている場合に限り、この形式を含めます。

## ステップ 4 — この契約に従って回答する

必ず次の構成で日本語で回答します。項目が本当に該当しない場合も、黙って省略せず、該当しないと
明記します。

````markdown
## 状態
FOUND | AMBIGUOUS | UNDEFINED | BLOCKED

## 手順
<何をする手順か、1 行>

## 出典
- `<path>` の `<target / 節 / job 名>`

## 前提条件
- <満たしていなければならないこと、必要な権限>

## コマンド
```bash
<正規に定義されたコマンド。存在するものだけ>
```
<UNDEFINED の場合は「なし」と書き、もっともらしい候補を提示しない理由を 1 行添える>

## 近いもの
- `<target / 手順>` — <ただし〜の点で目的が異なる>（FOUND 以外の場合に記載）

## 成功の判定
<どうなれば成功か>

## 復旧 / 切り戻し
<既存資料に定義されたもの。無いなら「定義なし」と書く>

## 注意
- <破壊性 / 環境差 / 共有インフラへの影響 / 未検証の点>

## 探索範囲
<通読したレジストリ / 確認した所有スキル / 検索した glob / 回さなかった掃引とその理由>
<UNDEFINED / AMBIGUOUS の場合は必須>

## エスカレーション
<未定義・矛盾・権限超過のとき、誰が何を決めれば進むか>
````

4 つの状態を次の意味で厳密に解釈します。

| 状態 | 意味 |
| --- | --- |
| `FOUND` | 正規手順が存在し、上記へ再掲または振り分けられている |
| `AMBIGUOUS` | 複数の候補があり、出典から 1 つを選べない。すべてを示し、どれも選ばない |
| `UNDEFINED` | すべての所有レジストリを全文読み、正規手順が存在しない |
| `BLOCKED` | 手順は存在するが、要求された操作が現在の権限を超える |

`UNDEFINED` は、すべての所有レジストリを全文読み、正確な探索範囲を公開した場合にのみ使用します。
それ以外では `AMBIGUOUS` または `確認できず` とし、未読の索引をすべて明示します。誤った
`UNDEFINED` はリポジトリの事実として提示されるため、探索範囲が不完全なら必ず状態を下げます。

`UNDEFINED` の場合、`コマンド` には **なし** と書き、もっともらしい候補を提示しない理由を 1 行
添えます。空欄にすると、次の読者にコマンドを自分で補うよう促し、このスキルが防ぐ失敗を一段後で
再発させます。検分して退けた惜しい候補は `近いもの` に記録し、その目的がどの点で異なるかも
明記します。「手順がない」とだけ伝えられた読者は再び探し始め、このスキルがすでに検分して退けた
候補を見つける可能性が高いためです。

## ステップ 5 — run モードでのみ実行する

`--mode=lookup` では手順のコマンドを実行しません。手順そのものが成果物です。

`--mode=run` では、許可された非破壊的なステップを実行します。このフラグは手順を許可するもので、
各破壊的ステップを許可するものではありません。各破壊的ステップの前に、何を破壊または変更するかを
日本語で正確に説明し、たとえば次のような番号付き選択肢を対話本文に提示します。

1. 実行する
2. このステップを中止する

続行する前に、ユーザーの番号による回答を待ちます。モーダルや Claude 固有の確認ツールが表示される
とは説明しません。対話中のユーザーがいない場合は、そのステップを `BLOCKED` と報告し、承認を
推測してはいけません。

データベースの drop、再帰的な所有権変更、共有 compose service の停止、その他の共有または不可逆な
変更は、破壊的操作として扱います。不足しているツールを独断でインストールしてはいけません。
不足ツールは報告すべき発見事項であり、このリポジトリでは通常、既存の機能が正規の `make` target
として公開されています。

## 単独で完結する設計

手順を引き渡して停止します。既知の落とし穴によって手順が阻害された場合は `repo-ops`、要求が
知識についての問いへ変わった場合は `repo-truth`、不足している手順を追跡すべき可能性がある場合は
`new-issue` というように、必要に応じて次の所有スキルの名前を挙げます。呼び出すかはユーザーが
選びます。

振り分け先のスキルをこのスキルへ取り込んではいけません。たとえば `new-env` へ振り分けることが
答えのすべてです。その手順をここへコピーすると、このスキルが防ぐべき重複が生まれます。

## すること / しないこと

- `--mode` がなければ `lookup` とみなし、何も実行しません。
- 最初に所有スキルへ振り分け、所有スキルがあれば停止します。
- キーワード検索より前に、索引を通じてレジストリを読みます。
- 前提条件、成功判定、復旧、注意事項の出典を個別に確認します。
- 各ステップの根拠となるファイルと target、節、または job を引用します。
- 共有インフラへの影響と、`DRY_RUN=1` への明示的な対応を毎回確認します。
- `UNDEFINED` では探索範囲を公開し、それができなければ状態を下げます。
- `UNDEFINED` では `コマンド` に理由とともに `なし` と書き、検分して退けた惜しい候補を、目的の
  相違点とともに `近いもの` へ記載します。
- 意図して回さなかった掃引は、その理由とともに `探索範囲` へ記録します。
- 各破壊的ステップの前に警告し、番号付き選択肢を提示して待ちます。
- 日本語で回答します。
- コマンド、flag、target、rollback、成功判定を発明しません。
- 別のスキルが所有する手順を再記述しません。
- キーワード検索や一部しか読んでいない索引から `UNDEFINED` と報告しません。
- 矛盾する authoritative source から 1 つを選びません。両方を示してエスカレーションします。
- lookup のみを求められたコマンドを実行しません。
- ツールがないという理由だけでインストールしません。
