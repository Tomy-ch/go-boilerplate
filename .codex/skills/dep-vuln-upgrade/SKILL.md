# Targeted Dependency Vulnerability Upgrade

Accept an advisory list from the user message. It may contain one line per package
(`package current → fixed (CVE/GHSA)`) or audit output. Parse package, installed version if
given, fixed candidates, advisory IDs, and severity; deduplicate a package with several
advisories. Change only advisory-named packages and mechanically required output.

The repository has four independent resolution surfaces:

- **npm:** `mock-auth-server/package-lock.json`; direct dependencies are in its `package.json` and
  transitive fixes may need a scoped `overrides` entry there.
- **pnpm:** `scripts/pnpm-lock.yaml` and `docs-viewer/pnpm-lock.yaml`; each directory's
  `pnpm-workspace.yaml` owns its cooldown, `overrides`, and release-age exclusions.
- **Go:** `go.mod` and `go.sum`, including indirect modules.
- **PyPI:** CLI tool declarations in `python/*.in`, resolved with sha256 hashes in `python/*.txt`.
  Locate these entries here, but never bump them here: `/tools-upgrade` owns the declaration and
  `make py-lock` regeneration.

Use `/tools-upgrade` for routine tool-version audits and PyPI declaration changes, `/go-upgrade`
for the Go language version, and `make tidy-lib` for a general Go dependency refresh.

## Allowed Write Surface

While this skill runs, modify only approved advisory-related package manifests, npm/pnpm lockfiles
regenerated by their package manager, `go.mod` / `go.sum`, and `vendor/**` only as the output of
`go mod vendor` when `vendor/modules.txt` exists. Regenerate a generated artifact only through its
existing `make` target when a dependency-driven drift check proves it changed.

Never hand-edit generated output, lockfiles, vendored files, `node_modules/**`, `python/*.in`, or
`python/*.txt`. Never change unrelated packages. In `pnpm-workspace.yaml`, write only `overrides`
and an explicitly approved `minimumReleaseAgeExclude` entry; never alter `minimumReleaseAge`,
`minimumReleaseAgeStrict`, `minimumReleaseAgeIgnoreMissingTime`, `trustPolicy*`, `allowBuilds`,
`blockExoticSubdeps`, or `engineStrict`.

## 1. Locate and Classify

Find every location that resolves the named package; do not infer ecosystem from its name. Search
all `package-lock.json` and `pnpm-lock.yaml` outside `node_modules`. In npm, the lockfile establishes
presence and `package.json` establishes directness. In pnpm, `importers:` identifies direct
dependencies and `packages:` / `snapshots:` records resolved transitive packages. In Go, `go.mod`
and its `// indirect` marker establish directness. For Python, a match in `python/*.in` is a declared
tool; a match only in `python/*.txt` may be transitive.

Record an entry per location: ecosystem, directory/file, installed version, direct/transitive or
indirect status, advisory IDs, and fixed candidates. A package may be present in several lockfiles.
Report an entry absent from all four surfaces as `not-present`; do not invent a location.

For a PyPI advisory:

- If `python/*.in` declares the tool, report its fixed version and declaration path, then hand the
  bump to `/tools-upgrade`. The governing policy is `tool-cooldown`; its escape hatch is
  `.github/tool-cooldown-bypass.toml`, neither writable by this skill.
- If only `python/<tool>.txt` resolves the package, report the carrying tool lockfile and whether a
  newer tool version resolves beyond the advisory. There is no per-package pin: wait for upstream
  or raise the parent tool through `/tools-upgrade` after the user decides.
- Never hand-edit `.txt`: `--require-hashes` makes an edited hash lockfile fail installation.

## 2. Select and Gate the Fixed Version

Choose the smallest fixed version on the installed major line. Never downgrade. Mark an only-higher-
major fix as `major-bump` and `needs-manual` when no non-downgrade candidate is available. For a
range, gate the version that the lockfile actually resolves; without a hard cooldown, pin the exact
approved direct version when a range would float to a too-new version.

Resolve `<MIN_AGE_DAYS>` **per lockfile**, preferring the repository's declared policy. Ask the user
explicitly only when no authoritative on-disk policy resolves a genuine ambiguity; state the default
of seven days for an ungated Go or package-manager location unless the user supplied a value.

- **npm:** read that lockfile directory's `.npmrc` `min-release-age=N`. It hard-blocks fresh
  resolution; there is no per-version escape hatch.
- **pnpm:** read the adjacent `pnpm-workspace.yaml` `minimumReleaseAge` in minutes (`10080 / 1440 =
  7` days), `minimumReleaseAgeStrict`, and every `minimumReleaseAgeExclude` entry. An existing
  exclusion covering the candidate makes it `clear`, not `blocked`. pnpm checks the whole lockfile
  on every install, including `--frozen-lockfile`; an in-window package breaks CI and every checkout,
  not merely the machine resolving it. See `docs/design/security.md` → Dependencies for details.
- **Go and ungated locations:** the age threshold is a caution window, not an installation block.

Fetch each candidate's publish date and classify it:

| Disposition | Condition | Action |
| --- | --- | --- |
| `clear` | Aged enough, or already in pnpm's exclusion list | Eligible. |
| `too-new` | Inside caution window without an npm/pnpm hard policy | Eligible only by explicit opt-in. |
| `blocked` | Inside `.npmrc` `min-release-age` or pnpm `minimumReleaseAge` | Defer; report `publish date + threshold`. |
| `major-bump` | Fixed version changes installed major | Requires explicit approval even when clear. |

Never lower or bypass a cooldown. A blocked npm package means wait or choose an older aged fixed
version. A blocked pnpm package may be offered a version-specific exclusion, but an existing
precedent is not approval to add another one.

## 3. Triage Caught Candidates and Decide

For **every** `too-new` or `blocked` entry, invoke `/supply-chain-triage` once before presenting a
decision. Provide ecosystem, package, candidate, lockfile baseline version, per-lockfile threshold,
disposition, and advisory. Triage is read-only and supplies its 0–12 band and evidence; it never
authorizes adoption.

Present a Japanese summary grouped by disposition. Then ask the user explicitly with one multi-select
question only if a `major-bump`, `too-new`, or blocked pnpm entry exists. Make every option deselected
by default and include its triage band in the option description (for example, `1/12 LOW`, `7/12 HIGH`,
or `INSUFFICIENT-EVIDENCE`). For a pnpm exclusion option, say both that it installs the version now
and that every checkout carries the policy exemption until somebody removes its line.

- Apply `clear` and non-major entries immediately without a question.
- Apply a major or too-new entry only when selected.
- Never apply a deferred item unilaterally. For npm, report the clearing time. For pnpm, offer the
  exclusion-or-wait decision; do not add it without approval.
- If no eligible package exists, make no writes and proceed to the report.

## 4. Apply Approved Changes

Batch approved entries by package directory. Read the resulting diff; do not accept unrelated
re-resolution churn.

**npm direct:** update the declared dependency, then run `npm install --package-lock-only` in its
directory. Re-read the resolved lockfile version and re-gate it. Do not hand-edit `package-lock.json`.

**npm transitive:** add the narrowest offending-parent-scoped `overrides` entry to `package.json`.
Use a same-major floor (`>=<fixed> <<next-major>`), not an exact pin, unless a documented newer
in-range version is known broken. Preserve sibling overrides and run `npm install --package-lock-only`.
Treat every override as provisional debt: remove it after its parent natively ships the fix.

**pnpm direct:** set the exact version in that directory's `package.json`, because these packages use
exact pins, then run `pnpm install --lockfile-only`. It rewrites `pnpm-lock.yaml` without materializing
`node_modules`; a normal bump changes only a handful of lines, so investigate a wide diff.

**pnpm transitive:** add an `overrides` entry only to `<dir>/pnpm-workspace.yaml`, never
`package.json`, and regenerate with `pnpm install --lockfile-only`. pnpm `parent>child` selectors and
resolution-range selectors do not have npm's nested-override semantics: never copy a scoped npm
override unchanged. Follow existing local form; when the needed transitive selector is not obviously
expressible, stop and report it for human decision rather than inventing one. Record the override as
provisional debt to reclaim when the parent ships the fix.

**Approved blocked pnpm version:** add a `minimumReleaseAgeExclude` item to every affected
`pnpm-workspace.yaml` in this form, retaining all existing entries:

```yaml
minimumReleaseAgeExclude:
  - <pkg>@<version> # Remove after <publish date + age threshold, JST>; <CVE/GHSA>; <runtime location>.
```

Use `pkg@version`, never a bare name. Include the JST removal time, advisory, and runtime exposure
(browser bundle, tool-runner build step, or service runtime). Do not change the release-age policy.

**Go:** batch approved modules in one `go get module@version ...`, then `go mod tidy`. Run
`go mod vendor` only when `vendor/modules.txt` exists.

## 5. Verify

Run checks matching changed ecosystems and report each result; do not auto-revert on failure.

- npm: `npm audit` in each changed directory; for a major bump also run that package's typecheck and
  tests. If audit needs a higher floor, surface it rather than silently selecting a too-new version.
- pnpm: in each changed directory run `pnpm install --frozen-lockfile`, then `pnpm audit`. A frozen
  install proves that policy permits replay in CI; an age-violation means an affected workspace lacks
  its necessary exclusion.
- Go: run `go build ./...` and `govulncheck ./...` when available; add `make lint` and `make test`
  when the Go change is broad enough.
- For generator-feeding dependencies, run the existing generator target and check generated drift.
  For a changed `scripts/` pnpm manifest, lockfile, or workspace file, run `make tool-runners-build`
  before claiming a containerized gate passes.

## Final Report

Report in Japanese: patched packages by ecosystem and location; versions and advisory IDs; provisional
overrides and their reclaim condition; each major, too-new, deferred, or exclusion decision; required
JST removal times for exclusions; every triage band and unanswerable axis; PyPI and not-present/manual
follow-ups; generated drift; tool-runner image rebuild status; and each verification result.

Do not stage, commit, push, broaden the patch beyond advisory-named dependencies, or start a
follow-up synchronization.
