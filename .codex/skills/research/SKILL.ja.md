# Research

未決の問いを人間が判断できる比較へ変換する。または、既存の決定や同型の前例によって、その問いが
すでに解消されていると確定する。

## 使用する場面

次の場合にこのスキルを使う。

- 設計・技術・運用の選択が未決である。
- 選択肢または一般的な方法を求められている。
- 以前の決定を明示的に見直し、トレードオフを比較し直す必要がある。

リポジトリの現状確認、決定済み issue の実行、結果の起票、変更レビューには使わない。それぞれ
Codex 側の `repo-truth`、`impl-issue`、`new-issue`、または該当する `impl-review` / `test-review` /
`comment-sweep` へ委ねる。これらの他スキル参照は `.codex/skills/<name>/SKILL.md` を指す。同期が完了
していない場合、Codex 側の複製が別環境より古い可能性があるため、依存する前に現在の契約を確認する。

## 契約

| | |
| --- | --- |
| **Owns** | 未決の比較、評価軸の確定、推奨とその反転条件、決めるべきことの提示 |
| **Never** | 採択 / ADR 承認 / 実装 / 案数合わせの選択肢捏造 / 出典・数値の捏造 |
| **Starts when** | 選択が開いていて、まだ誰も決めていないとき |
| **Stops when** | 現状が不明（`repo-truth` へ）、既に ADR / spec が決めている、外部情報を確認できない |

停止時は、検証済みの結果と未解決の境界を報告する。仮定で隙間を暗黙に埋めず、採択や実装へ進まない。

## このスキルが存在する理由

慎重に見えながら比較を壊す、次の 4 つの失敗を防ぐ。

1. **答えに合わせた評価基準。** 好ましい答えが先にあると、それを支持する基準だけが記録される。
   どの案も挙げる前に評価軸を固定する。
2. **コストに選ばせた結論。** コストは重要な範囲情報だが、このリポジトリの `AGENTS.md` では、
   template の品質と一貫性が、そこへ至る作業量に優先する。人間が方向を変えず範囲を断れるようコストを
   述べるが、推奨を選ぶ重みにはしない。
3. **発明された根拠。** もっともらしいベンチマーク値、バージョン、日付、引用は根拠ではない。
   未検証のものは明示し、それに依存する結論の確度を下げる。
4. **捏造された分岐。** 既決事項または構造的に同一の仕組みが配置・構築・呼び出しをすでに決めているなら、
   採点対象は存在しない。

## 引数

| 引数 | 挙動 |
| --- | --- |
| `--stage=full` *(既定)* | 比較と推奨まで進める |
| `--stage=dissolve` | 既決事項と同型前例の確認だけを行って停止する |
| `--sources=repo` | リポジトリ内の根拠だけを使い、検証できない外部主張は省く |
| `--sources=external` *(既定)* | 後述の出典規則に従って外部調査を許可する |
| `--axes=<csv>` | Step 2 で選ぶ代わりに、呼び出し元が指定した評価軸を使う |

問いが本当に未決かを確認したい場合、`--stage=dissolve` を安価だが完全な結果として扱う。
`--sources=repo` は明示的な根拠境界であり、記憶から外部情報を補う許可ではない。この境界のために
述べられなかった主張を明記する。

## Step 0 — 選択が未決であることを確かめる

現在何が存在するか、どの規則が制約するか、`docs/adr/` または `docs/design/` に決定があるかを
確認する。リポジトリの状態が不明または争われているなら停止し、`repo-truth` の実行を案内する。
自動的にそのスキルを呼び出してはならない。

ADR または spec がすでに決めているなら、その決定を報告し、記録された前提が今も成り立つかを評価して
停止する。既決のアーキテクチャ・ドメイン・ポリシー判断を再び開けるのは人間だけである。

ユーザーの問いに含まれる単語だけでなく、各記録が所管する関心事から決定索引を探す。
`docs/adr/README.md` と `docs/design/README.md` を読み、所管範囲から関連項目を選ぶ。別名の統治文書を
見落とすと、明白なエラーではなく偽の比較が生まれる。

## Step 1 — 構造から問いの解消を試みる

設計分岐だと扱う前に、リポジトリ内の別の場所に同じ構造の仕組みがないか探す。所管レイヤー、その兄弟
パッケージ、次に `pkg/` を数え上げ、語彙ではなく形を見る。実行時に `docs/architecture.md` と最寄りの
所管 `README.md` を読む。

同型前例が無関係なドメイン語彙を使うことがあるため、キーワード検索だけでは不十分である。たとえば page
cursor は「window」という語を共有せずに time window に必要な形を確定できる。利用可能ならリポジトリの
グラフで構造を探索し、候補は必ずソースで確認する。

```bash
# Reverse traversal: callers and load-bearing relationships.
node .claude/scripts/graph-affected.ts <symbol> --depth 2

# Structural query. The default budget is too small for this repository.
GRAPHIFY="${XDG_CACHE_HOME:-$HOME/.cache}/go-boilerplate/graphify/bin/graphify"
"$GRAPHIFY" query "<structural question>" --budget 8000
```

グラフの挙動は、Claude 側の `.claude/README.md` に環境非依存のリポジトリ知識として記録されている。
そのファイルを参照する。グラフの edge は手がかりであり、同型性の証明ではない。
`graphify-out/GRAPH_REPORT.md` の `Built from commit:` と `git rev-parse HEAD` を比較する。グラフが
存在しない、または古い場合、前例なしという主張が弱くなるため明示する。

見つけた前例は独立に検査できる。一方、前例が存在しないという主張には探索範囲が必要である。数え上げた
全レイヤーとパッケージ群を示す。構造探索が部分的なら、分岐が実在すると断定せず、比較を暫定扱いにする。

前例によって問いが確定する場合、日本語で次のように報告して停止する。

> 設計分岐なし。`<X>` は既存の `<Y>` と同型で、配置・構築・呼び出し位置はそちらの前例で確定する。

`--stage=dissolve` では、問いが解消したか実際に未決だったかにかかわらず、この Step の後で停止する。

## Step 2 — 選択肢より先に評価軸を固定する

案を 1 つも挙げる前に、この問いの評価基準を選んで公表する。公表後は、見えてきた答えを有利にするために
変えない。`--axes=<csv>` が指定された場合、その軸を採用し、それぞれが問いにどう関係するかを説明する。

このリポジトリで有用な出発点は次のとおりである。

- 業界的正しさ
- DDD 整合性
- アーキテクチャ純粋性
- template 先の純粋性

これは固定の採点表ではない。build gate の問いに DDD の次元がない場合もあり、語彙の問いはほぼ DDD だけで
決まる場合もある。この問いを決める軸だけを残し、すべての採用理由を説明する。

立てなかった軸と、その理由も記録する。軸がない理由は、その問いがその軸では決まらないためか、この実行では
評価に必要な根拠を用意できなかったためかのどちらかである。たとえば `--sources=repo` では、外部根拠を要する
業界的正しさの軸を扱えない。この区別がなければ、読者は無関係だったのか根拠が不足したのかを判別できない。
比較の形そのものが、何を重要と見なしたかという主張である。

リポジトリの実際の成果物を常に考慮する。それは `useTemplate` 時点に、履歴を知らず Git log も読まない
利用者が受け取る、一貫した snapshot である。

## Step 3 — 実在する選択肢だけを列挙する

案数を固定しない。導入する / しないという二値の問いには 2 案が正しい。実質的に異なる方法が 5 つなら 5 案
必要である。3 案にするため藁人形を足さず、表を短くするため本物の差異を隠さない。統合するのはほぼ同じ案だけ
である。

固定した評価軸に対して各案を比較し、次を含める。

| 項目 | 必須内容 |
| --- | --- |
| 案 | 記号ではなく内容を表す名前 |
| 利点 / 欠点 | 形容ではなく観測可能な帰結 |
| リスク | 失敗形態、移行、運用、セキュリティ、ロックイン |
| 既存構造との整合 | 所管レイヤー、該当する `docs/rules.md` の規則、下流への影響 |
| コスト | 影響ファイル、壊れる対象、必要な再生成。結論の重みにはしない |

検証できる主張は測定する。hot path に read が増えると述べるだけでなく query 数を数える。おおよその
ファイル数を発明せず、逆向きグラフ走査で blast radius を見積もる。測れなかったコストは `未確認` に置き、
測れなかった理由と、測れば何が変わるかを併記する。コスト欄に但し書き付きの見積もりを残してはならない。
但し書き付きの数字も数字として読まれ、意思決定へ持ち込まれるためである。

## Step 4 — 推奨と反転条件を示す

1 つを推奨し、固定済みの評価軸と検証済みの根拠へ結び付ける。中立的な一覧だけでは分析の負担を人間へ
戻してしまう。

次に、推奨を反転させる事実を示す。不確実性を、たとえば次のような反証可能な条件で表す。

> この推奨は、`<前提>` が成り立つ限り。`<条件>` なら B が優位に転じる。

推奨は助言であり、採択してはならない。

## Step 5 — 意思決定パケットを返す

ユーザー向け出力は日本語で書き、推奨を先頭に置く。次の見出しと意味を使う。

```markdown
## 問題
<何を決めようとしているか、1〜2 文>

## 前提
- <置いた仮定と、それが崩れたときの影響>

## 評価軸
- <軸> — <なぜこの問いでこの軸なのか>
- 立てなかった軸: <軸> — <なぜこの問いでは立てられない / 関係しないのか>

## 選択肢
### <案の名前>
- 利点 / 欠点 / リスク / 既存構造との整合 / コスト

## 推奨
<どれを、なぜ>

## 推奨が変わる条件
- <この事実が違えば結論が変わる>

## 未確認
- <測れなかったコスト / 確認できなかった主張> — <なぜ測れなかったか、測れば何が変わるか>

## 決めるべきこと
- <人間が決める事項> — 記録先: ADR / issue / spec のどれか

## 出典
- <発行主体> 「<資料名>」 <URL> （参照 <日付>）
```

人間が案を選ぶ必要がある場合、通常の対話本文に実在する案を番号付きで示し、返答を待つ。modal や
Claude 固有の質問 API を前提にせず、沈黙を承認と解釈しない。

問いが解消した場合または途中で停止した場合は、作業で裏付けられた節だけを返す。未調査部分と次に必要な
人間の行動を明記する。完全に見える回答より、正確な部分回答を優先する。

## 出典

外部主張には、発行主体、資料名、URL、参照日を付ける。仕様、プロジェクト公式文書、release note などの
一次・公式資料を優先する。外部参照を許可された場合、実行環境のブラウジングと引用の規則に従う。

参照に失敗した、または主張を確認できない場合は未検証と明記し、それに依存する結論の確度を下げる。
benchmark 結果、version、非推奨日、引用、出典を捏造してはならない。

リポジトリ内の根拠は行番号ではなく path と symbol を示す。根拠と推論を分ける。

## 単独で完結する設計

`決めるべきこと` で終える。案の採択、ADR の作成・承認、issue の起票、spec の変更、実装開始を行わない。
`repo-truth`、`new-issue`、`impl-issue` を自動的に連鎖させない。

このスキルの後は、人間が案を承認し、指定された正本へ記録し、その後に適切な issue または実装 workflow を
使う。承認を求める場合、回答内に番号付きの案を示して待つ。

## チェックリスト

- [ ] `--stage`、`--sources`、呼び出し元が指定した評価軸を解決した。
- [ ] `--sources=repo` では、意図的に省いた外部主張を明記した。
- [ ] 現状を確定した。または停止して次の手順に `repo-truth` を示した。
- [ ] `docs/adr/README.md` と `docs/design/README.md` を所管する関心事から読んだ。
- [ ] 既存 ADR または spec の決定を報告して停止した。
- [ ] 数え上げたレイヤーで同型機構を形から探し、最新ならグラフも使った。
- [ ] 前例なしと主張する前に、数え上げた探索範囲を示した。
- [ ] 案を挙げる前に評価軸を固定し、採用理由と意図的に立てなかった軸の理由を説明した。
- [ ] 確認できなかったコストと主張を、但し書き付きで本文へ混ぜず `未確認` に置いた。
- [ ] 目標数を置かず、この問いに実在する案を列挙した。
- [ ] 各案に帰結、リスク、構造との整合、コストを示した。

- [ ] 推奨、根拠、反転条件を示した。
